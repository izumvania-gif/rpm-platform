# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**RPM Platform** (renamed from "ECHO Platform" on 2026-08-06; repo name `rpm-platform` already matched the new name — rename applied across UI and code) — a product discovery / research management tool for product managers, at 1.0 as of 2026-08-07. Core loop: research repository → customer segments → JTBD (with a hierarchy + sequence graph canvas, independently laid out per segment) → hypotheses (kanban board) → CustDev conversations, plus a product-positioning layer (competitors with a news log, features, RTB/"Маркетинг"). Most of this is now built, not planned — see `PROJECT_STATE.md` for a short snapshot of what exists today, `plans/backlog.md` for what's deliberately deferred or not built (AI features, auth/multi-tenancy, etc.), and `plans/ui-improvement-plan.md` for known UI polish opportunities. The full build history (including the ECHO → RPM rename and the original ECHO spec) lives in `plans/archive/` — `plans/archive/growth-plan.md` is the single largest source of "why is it built this way" detail if a §-numbered reference below needs more context. Product-facing text (UI copy, docs) is in Russian; code, identifiers, and comments are in English. **End-user documentation** (Russian, written from a working PM's perspective — daily workflow, step-by-step scenarios, field/relationship reference, recommendations and known limitations) lives in `docs/user-guide/` — update it alongside `PROJECT_STATE.md`/`plans/backlog.md` when a change affects what a user sees or does, not just what's built.

**Information architecture:** top nav (`components/shared/site-nav.tsx`) is 5 main tabs — Продукты, Сегменты, Исследования, Маркетинг (renamed from RTB; route is `/marketing`, the Prisma model is still called `RTB`), JTBD. Продукты and Исследования have a hover/focus dropdown sub-menu (Фичи + Конкуренты; Гипотезы + Разговоры + Инсайты respectively). Competitors was deliberately left out of the nav at first (§2.1) — `/competitors` existed as a route linked only from a product's detail page — but that decision was reversed by direct product-manager instruction (§2.9.3): Competitors is now a "Продукты" sub-link alongside Фичи, and the `g k` keyboard shortcut (`components/shared/keyboard-shortcuts.tsx`) points at it again. JTBD has its own tab (not nested under anything) with an in-page "Список"/"Граф" tab switcher (`components/shared/jtbd-view-tabs.tsx`) between the plain list and the graph canvas — the graph itself has a further per-view switcher (overall vs. a specific segment, §2.9.1) with independently-persisted node layouts per view. A GET-form search box lives in `SiteNav` itself (`/search?q=`, plain `contains`-based Prisma queries across all 11 content models, no full-text search infra). Read-only analytical pages live outside the CRUD-module URL convention, under `/reports` (`/reports`, `/reports/segments-jtbd`, `/reports/gaps`) — kept separate from `/insights`, which is the actual `Insight` CRUD module, to avoid the two colliding in the URL space.

## Commands

```bash
npm run dev           # dev server (http://localhost:3000)
npm run build          # production build
npm run start           # run production build
npm run lint            # next lint (ESLint)
npm run format           # prettier --write on ts/tsx/js/jsx/json/css/md

npm run db:push          # push Prisma schema to DB (no migration file) — used in dev
npm run db:migrate       # create + apply a Prisma migration
npm run db:generate      # regenerate Prisma Client (run after editing schema.prisma)
npm run db:studio        # Prisma Studio GUI

npm run typecheck        # tsc --noEmit
npm run test             # alias for test:unit — no DB needed
npm run test:unit        # Vitest, lib/validation.ts + lib/utils.ts
npm run test:integration # Vitest, all lib/actions/*.ts against a real Postgres test DB
npm run test:e2e         # Playwright, browser-driven flows against `next dev`
```

Requires a running PostgreSQL 15+ instance and `DATABASE_URL` set (copy `.env.example` to `.env.local`). See `## Testing` below for the test pyramid and the separate test-database setup `test:integration`/`test:e2e` need.

## Architecture

- **Next.js 14 App Router, fullstack monolith.** UI and API both live under `app/`; API routes are Next.js Route Handlers (e.g. `app/api/auth/[...nextauth]/route.ts`). There is no separate backend service — an AI service (originally scoped as Python/FastAPI) is in `plans/backlog.md` but architecturally not started; no AI dependency exists anywhere in the current stack.
- **Data layer:** Prisma ORM against PostgreSQL, schema in `prisma/schema.prisma`. Eleven content models today — `Product`, `Research`, `Segment`, `JTBD` (+ `JtbdSequenceEdge` for the graph, + `JtbdGraphLayout` for persisted per-view node positions — see `plans/archive/growth-plan.md` §2.9.1; JTBD↔Segment is many-to-many, not a single `segmentId`), `Hypothesis` (+ `HypothesisStatusChange`), `Conversation`, `Competitor` (+ `CompetitorNewsItem`, a manual news/observations log — §2.9.4), `ProductResource`, `Feature`, `RTB`, `Insight` (atomic quotes/conclusions, optionally linked to a segment/JTBD/research/conversation) — each scoped to a `userId` (single-tenant MVP — no workspace/org model yet, `where: { userId }` is repeated by hand in every query, not enforced by a shared layer). Import the shared client from `lib/prisma.ts` (`prisma` singleton guarded against hot-reload duplication) rather than instantiating `PrismaClient` directly. After changing `schema.prisma`, run `npm run db:generate` (and `db:push` or `db:migrate` to sync the DB).
- **Auth:** NextAuth.js with the Credentials provider (email + bcrypt-hashed password), JWT session strategy, configured in `lib/auth.ts` and mounted at `app/api/auth/[...nextauth]/route.ts`. Session/User/JWT types are augmented in `types/next-auth.d.ts` to carry `id` through `session.user.id` and the JWT token. In practice all data is currently read/written under one hardcoded `DEFAULT_USER_ID` (`lib/current-user.ts`) — the login flow exists but multi-user isolation hasn't been exercised.
- **UI components:** shadcn/ui, configured via `components.json` (style: default, baseColor: slate, CSS variables). `components/ui` holds shadcn primitives, redesigned as of Фаза 2 of `plans/visual-redesign-plan.md` (2026-08-07) — `select.tsx` is now a Radix-based (`@radix-ui/react-select`) drop-in replacement for the native `<select>` (same external API — `value`/`defaultValue`/`onChange`/`name`/`id`/`children`-as-`<option>` — no call sites changed; an empty-string option value is mapped to a sentinel internally since Radix forbids `value=""`), `button`/`card`/`badge`/`input`/`textarea` have refined variants/focus states, and `badge.tsx` exposes the `--signal-violet/red/blue/slate` palette as first-class variants (`JobTypeBadge`/`SignalBadge` are now thin wrappers over `Badge`). `lucide-react` icons are wired onto every dashboard module tile (`lib/module-meta.ts`'s `ModuleMeta.icon`). Playwright can't use `.selectOption()` against the new Select (it's a styled trigger + portal listbox, not a native control) — `e2e/helpers.ts`'s `selectRadixOption`/`selectOptionRobust` click through `role="option"` instead; see Фаза 2's write-up in the plan for the `getByText`-vs-`getByRole` pitfall this migration surfaced (a Radix-rendered hidden native `<select>` mirror is excluded from the accessibility tree but not from DOM-text search). `components/forms`, `components/shared`, `components/jtbd-graph`, `components/hypotheses` hold feature components — most of `components/forms/*` (Фаза 4) lay out fields in a `max-w-2xl` `grid sm:grid-cols-2`, pairing short scalar fields and giving `sm:col-span-2` to long ones (Textarea, tag/relation checkbox lists); skip the grid for a form with too few short fields to pair (e.g. `rtb-form.tsx`). `lib/utils.ts` provides the standard shadcn `cn()` helper (clsx + tailwind-merge). Theme is a red/off-white "Rutoken corporate" palette driven by CSS variables in `app/globals.css`, including `lib/jtbd-job-types.ts`'s job-type colors (`--jtbd-*` variables) and a signature `--ease-signature` transition curve wired as Tailwind's default `transitionTimingFunction`. Dark mode works — `.dark` on `<html>` is toggled by `components/shared/theme-toggle.tsx`, defaults to `prefers-color-scheme`, persisted in `localStorage`, applied before hydration by an inline script in `app/layout.tsx` (avoids FOUC).
- **Path aliases:** `@/*` maps to the repo root (see `tsconfig.json`), e.g. `@/lib/prisma`, `@/components/...`.
- **Mutation pattern:** most create/update actions in `lib/actions/*.ts` are Server Actions that `redirect()` on success. Anywhere the UI must stay on the current page (inline-create pickers, the JTBD graph canvas, the hypothesis kanban board, the product onboarding wizard), there's a second non-redirecting variant — `createXQuick(...)` — returning `{ ok: true, data } | { ok: false, error }`, paired with `useTransition` on the client (state is appended locally rather than via `router.refresh()`, in the wizard's case). All 9 content models now have one. Don't export plain data/option arrays from a `'use client'` file for a Server Component to consume — Next.js treats every export from a client-boundary file as an opaque client reference even for non-component data, which crashes at runtime; pass such arrays down as props from the server page instead (this has bitten the codebase twice).
- **Inline field editing** (§2.9.5): all 10 detail pages (`/products/[id]`, `/research/[id]`, `/segments/[id]`, `/jtbd/[id]`, `/hypotheses/[id]`, `/conversations/[id]`, `/competitors/[id]`, `/features/[id]`, `/marketing/[id]`, `/insights/[id]`) use `<InlineEditableField>` (`components/shared/inline-editable-field.tsx`) for click-to-edit-in-place on scalar fields, alongside a one-Server-Action-per-model `updateXField(id, field, value)` in the matching `lib/actions/*.ts`. The field's view-mode presentation (badge, tag pills, formatted date, link) is driven by serializable props (`display`, `labels`, `badgeVariant`, `prefix`/`suffix`) rather than a render-prop function — a Server Component (every detail page) cannot pass a plain function into a Client Component as a prop, only serializable data or a `'use server'`-bound action; that mistake doesn't surface until the browser actually renders the page, not at `tsc`/`next build` time, so watch for it when extending this component. Relation fields (JTBD segments, linked features, etc.) are out of scope for inline editing — they keep using the full edit form's multi-select.
- **Onboarding wizard:** `/products/[id]/onboarding/{segments,jtbd,research,hypotheses,competitors,features}` + `/done`, triggered by an explicit choice on the product-creation form (`ProductForm`'s `showOnboardingOption`, two submit buttons sharing one `name="mode"` field — no JS). Shared shell in `components/onboarding/wizard-shell.tsx` + `wizard-steps.ts`; each step is read-only/append-only (no inline delete — every existing `delete*` action redirects, which would break the wizard's stay-on-page flow). See `plans/archive/growth-plan.md` §2.6 for the full design and the trade-offs behind it.
- **Still genuinely not built** (do not assume these exist): NextAuth UI screens beyond the API route, AI chat/RAG features, an AI service of any kind, multi-language (EN) support, workspace multi-tenancy, deployment/CD automation. See `plans/backlog.md` for the full list and `plans/archive/ECHO_functional_requirements.md` for the original spec these were drawn from.

## Testing

Three layers, added 2026-08-07 (`.github/workflows/ci.yml` runs all of them on every push/PR):

- **Unit** (`tests/unit/`, Vitest, no DB) — pure functions only: `lib/validation.ts`'s FormData-to-Zod helpers, `lib/utils.ts`'s `slugify`/`transliterate`/`isStale`. Zod schemas themselves live inline per `lib/actions/*.ts` file (not centralized), so their validation behavior is exercised at the integration layer instead, through the action that owns each schema.
- **Integration** (`tests/integration/`, Vitest, real Postgres) — one file per `lib/actions/*.ts`, covering every exported Server Action's happy path plus at least one validation-failure case, against a real (not mocked) test database — required because the schema uses native Postgres enums and array columns that an in-memory/SQLite substitute can't represent. `next/navigation`'s `redirect()` and `next/cache`'s `revalidatePath()` are mocked (`tests/integration/setup.ts`) since Server Actions call them unconditionally but there's no real Next.js request context outside the browser — `redirect()` throws a catchable `REDIRECT:<path>` signal instead (see `captureRedirect` in `tests/integration/helpers.ts`), letting tests assert the intended destination while still exercising the real DB write that precedes it. Every table is truncated before each test (`beforeEach` in `setup.ts`).
- **E2E** (`e2e/`, Playwright, real browser + Postgres, against `npm run dev`, not a production build — a `next build` static-export step has proven flaky specifically under Playwright's process spawning in sandboxed containers, so E2E deliberately runs against dev mode instead and CI verifies `next build` as a separate standalone step) — full user flows through the actual UI: CRUD, the JTBD graph canvas, hypothesis kanban drag-and-drop, the onboarding wizard, search, reports, keyboard shortcuts. Specs run sequentially (`workers: 1`) against one shared test database with no per-spec reset, so every spec names its records with `uniqueName()` (`e2e/helpers.ts`) rather than assuming a clean slate.

**Local setup for `test:integration`/`test:e2e`:** copy `.env.test.example` to `.env.test`, point it at a separate throwaway database (never the one `npm run dev` uses), `createdb` it, then `npm run db:push` against it once. Both `tests/integration/setup.ts` and `playwright.config.ts` refuse to run if `DATABASE_URL` doesn't contain "test", as a guard against ever truncating a real database by mistake — the dotenv load order (`.env` then `.env.test` with `override: true`) is load-bearing for this reason; changing it without keeping `override: true` silently repoints tests at whatever `.env` has set instead.

## Conventions

- No semicolons, single quotes, 2-space indent, 100-char line width, ES5 trailing commas — enforced by Prettier (`.prettierrc`); run `npm run format` rather than hand-formatting.
- ESLint (`.eslintrc.json`) extends `next/core-web-vitals` + `@typescript-eslint/recommended`, with `@typescript-eslint/no-explicit-any` as an **error** (not a warning) — avoid `any` types.
- TypeScript `strict` mode is on.
