# Заполнение данных: что осталось после `2.0-product-leap-plan.md`

Продолжение раздела A того плана. Там было закрыто «занести много **записей**».
Здесь — два разрыва, которые остались после него и обнаружились при попытке
занести реальный продукт руками.

## Разрыв 1: связи никто не умеет заносить пачкой

Все построенные до сих пор способы ввода создают **записи**: мастер настройки,
`BulkAddPanel` (A1), импорт CSV (A2), модалка быстрого захвата, `/inbox` (B1),
заготовки (A4). Ни один из них не создаёт **связь**.

А читает приложение именно связи:

| Что считает связи, а не записи | Где                                        |
| ------------------------------ | ------------------------------------------ |
| Цепочка дискавери              | `lib/discovery-chain.ts` + виджет дашборда |
| Матрица Сегменты × JTBD        | `/reports/segments-jtbd`                   |
| Отчёт «Пробелы»                | `/reports/gaps`                            |
| «Что мы можем сказать»         | `/marketing-hub`                           |
| Кросс-продуктовые корреляции   | `/cpo`                                     |
| Лента связей на записи         | `components/shared/chain-ribbon.tsx`       |

Замер на демо-наборе (`prisma/seed.ts`): 48 записей и **13 связей** между ними.
Каждая связь до сих пор ставилась через форму редактирования владельца связи —
открыть, долистать до списка чекбоксов, отметить, сохранить, получить редирект.
Это 2 полные перезагрузки на одну **запись** (не на связь), то есть ~28
перезагрузок, чтобы связать один демо-продукт.

### Решение: `/products/[id]/links` — «Связи»

Три сетки чекбоксов, по одной на каждую из трёх many-to-many связей в
`schema.prisma`. Больше их там нет — это не выборка «самого важного», а полный
список:

1. **JTBD × Сегменты** — строки JTBD, столбцы сегменты
2. **Фичи × JTBD** — строки фичи, столбцы JTBD
3. **Фичи × RTB** — строки фичи, столбцы RTB

Решения, которые стоит помнить:

- **Строка — длинная ось.** Таблица нормально прокручивается вниз и плохо
  вбок, поэтому по вертикали идёт та сущность, которая будет расти. Отсюда же
  повёрнутые на 90° заголовки столбцов: столбец шириной с чекбокс независимо
  от длины названия. Высота этой полосы считается из самой длинной подписи
  (`headerHeightPx`) — фиксированные 160px выглядели как ошибка вёрстки над
  таблицей из четырёх строк.
- **Ключевые фразы, как везде.** Строки и заголовки прогоняются через
  `jtbdKeyPhrase`; полный текст остаётся в `title`. Иначе шесть JTBD,
  обрезанных слева по шаблону «Когда …», выглядят одинаково.
- **Вердикт — «сколько строк вообще без связи»**, не процент. `4 без связи`
  — это то число, на которое реагируют все отчёты ниже по течению; `73%`
  не говорит, что делать.
- **Итог по столбцу в подвале.** Столбец, к которому не привязано ничего,
  внутри сетки неотличим от просто разреженного — сегмент без единой задачи
  видно только по нулю в подвале.
- **Оптимистичное переключение с откатом.** Галочка появляется до ответа
  сервера, иначе отметить сорок штук подряд — это сорок ожиданий. При ошибке
  клетка возвращается ровно на место и появляется текст ошибки: галочка,
  которой нет в базе, хуже отсутствующей галочки.
- **`denyUnowned` на обе стороны.** `rowId` и `colId` оба приходят от клиента.
  Проверка только строки оставила бы `jtbd.update({ segments: { connect } })`
  кросс-тенантной записью — интеграционный тест на это есть.

## Разрыв 2: пачкой нельзя было занести JTBD — самый массовый тип

`BulkEntity` покрывал 5 типов из 11. За бортом были JTBD и RTB.

RTB — просто пропуск: у него одно обязательное поле, он подходил под правило
«одна строка + продукт» с самого начала.

JTBD был исключён осознанно (комментарий в `lib/actions/bulk.ts`): ему нужна
категория, а придуманная категория попадает в матрицу покрытия и в «Пробелы»
так, как будто её выбрал человек. Но модалка быстрого захвата этот же вопрос
уже решила — она **спрашивает** категорию, а не выдумывает. Пачка решает его
так же, только один раз на весь список: PM вставляет шесть задач **одной**
категории, а не шесть несвязанных. Пока поле пустое, кнопка «Добавить»
заблокирована.

`jobType` остаётся на дефолте схемы `SMALL_JOB` — ровно то же решение, что
принимает `createJtbdQuick`, и единственное поле, которое потом правится
перетаскиванием в графе, а не редактированием формы.

В импорте CSV категория, наоборот, спрашивается **по строке**: в таблице для
этого уже есть колонка, и выгрузка `jtbd.csv` этого же приложения
(`category,jobType,title,product,confirmed,tags`) теперь возвращается обратно
без единого ручного сопоставления колонок.

### Инбокс остался на прежних типах

`/inbox` разбирает смешанный текст и угадывает тип каждой строки. JTBD туда не
добавлен: категорию по одной строке заметок честно не угадать, а вопрос «одна
категория на всю пачку» здесь бессмыслен — весь смысл инбокса в том, что
строки разнородные. Поэтому у него теперь свой тип `InboxEntity` — подмножество
`BulkEntity` без `jtbd`.

## Что осознанно не сделано

- **Матрица не заменяет форму.** Отношения, у которых есть собственные поля
  (`JtbdSequenceEdge`, `ProcessEdge`), в сетку не годятся — там связь это
  запись, а не галочка.
- **Массовый ввод людей (`Person`).** `createManyQuick` принимает `productId`,
  а `Person` живёт на уровне пользователя, а не продукта. Понадобится —
  добавлять как отдельный экшен, а не расширять этот.
- **Шаги мастера для Роадмапа / Процессов / Департаментов.** Мастер запускается
  только для **нового** продукта, а роадмап заполняется у уже живого; для него
  прямо на диаграмме Ганта уже есть лоток «не на диаграмме» и планирование
  перетаскиванием.
