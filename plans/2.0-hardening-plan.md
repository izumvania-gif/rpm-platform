# План улучшений RPM Platform 2.0 — техническая устойчивость и доступность

## Контекст

Ветка `2.0` функционально завершена: все 8 фаз `platform-views-plan.md` и все
6 фаз `2.0-ux-improvement-plan.md` сделаны. 32 тысячи строк, 75 страниц, 19
моделей, 179 интеграционных + 53 E2E теста — фича-покрытие хорошее.

Этот план — не про новые фичи. Это аудит того, что накопилось _под_ фичами за
время быстрой сборки 2.0, с приоритетом по риску. Всё ниже **измерено на
реальной кодовой базе и сид-данных**, а не выведено из общих соображений;
цифры и способ их получения указаны у каждой находки, чтобы их можно было
перепроверить.

**Осознанно вне рамок:** мобильный опыт (подтверждено с пользователем —
не приоритет сейчас), AI-фичи, деплой/CD, мультиарендность как продуктовая
функция.

## A. Технические находки

### A1. ✅ Сделано. 64 мутации без проверки владельца — критично, но пока латентно

**Что измерено.** Скрипт по всем `lib/actions/*.ts`, вытаскивающий каждую
экспортированную функцию, которая делает `where: { id }` и при этом ни разу не
упоминает `userId`:

```
64 функции в 20 файлах — каждый update*/delete*/toggle*Pinned/update*Field
```

Примеры (буквальный код, не пересказ):

```ts
export async function deleteProduct(id: string) {
  await prisma.product.delete({ where: { id } })   // ← кто угодно, любой id
  ...
}
export async function updateHypothesisStatus(id: string, status: HypothesisStatus) {
  await prisma.hypothesis.update({ where: { id }, data: { status } })
}
```

**Почему сейчас не эксплуатируется.** `lib/current-user.ts` возвращает
захардкоженную константу `'default-user'`, `getServerSession` не вызывается
нигде во всём репозитории (проверено `grep`), `middleware.ts` отсутствует.
То есть аутентификации сейчас нет вообще — не «есть, но однопользовательская».
NextAuth смонтирован как API-роут, но ничего его не проверяет.

**Почему это всё-таки главный пункт плана.** Ровно та строчка, которой
естественно включают аутентификацию —

```ts
export function getCurrentUserId() {
  return session.user.id // вместо DEFAULT_USER_ID
}
```

— мгновенно и молча превращает все 64 функции в IDOR-уязвимости. Чтения в
основном отфильтрованы (`where: { userId }` расставлен по страницам вручную),
поэтому чужие данные не отобразятся в списках — но их `id` угадывается или
утекает, а мутация по чужому `id` пройдёт без единой проверки. Тесты этого не
поймают (см. A5). Худший класс дефекта: включается не тем коммитом, который его
создал.

**Дополнительно:** часть чтений тоже не отфильтрована —
`prisma.processStep.findMany({ where: { process: { productId } } })` и
`prisma.productTeamMember.findMany({ where: { productId } })` в
`lib/team-workload.ts` полагаются на то, что `productId` уже проверен выше по
стеку, а он не проверен.

### A2. ✅ Сделано. N+1 в `getProductsOverview` — измерено 61 запрос вместо 3

**Что измерено.** Prisma-middleware, считающий операции на реальных сид-данных
(20 продуктов):

```
cpo: getProductsOverview        ops=  61   111ms
  разбивка: JTBD.count x40, Hypothesis.groupBy x20, Product.findMany x1
...
TOTAL /cpo Prisma ops = 75
```

61 = 1 + 3×20, то есть строго линейно по числу продуктов. При 50 продуктах —
151 операция, при 100 — 301, на каждую загрузку `/cpo`.

Причина — `Promise.all(products.map(async ...))` в `lib/cpo-metrics.ts:44`,
внутри которого на каждый продукт вызываются `getJtbdCoverage` (2 `count`) и
`getHypothesisStatusCounts` (1 `groupBy`).

**Исправление проверено на практике.** Прототип с тремя `groupBy` по
`productId` вместо цикла:

```
original : 37ms
batched  : ops=3  5ms
correctness: IDENTICAL across all 20 products
```

Три запроса вместо 61, ~7× быстрее, побайтово те же числа по всем 20
продуктам. Это не рефакторинг «на будущее» — это готовая замена.

### A3. ⛔ Осознанно не включено — премиса не подтвердилась замером

74 из 75 `page.tsx` объявляют `export const dynamic = 'force-dynamic'`.
`unstable_cache` не используется нигде, `export const revalidate` — нигде.
При этом `revalidatePath` вызывается **181 раз** в `lib/actions/*.ts`, то
есть инвалидация написана аккуратно и подробно — под кэш, которого нет.

Инфраструктура для кэширования уже фактически построена; включить его — почти
чистая выгода, особенно для агрегатов `/cpo` и `/reports`, которые не меняются
между мутациями.

### Фаза 4 — как сделано

**A2 реализовано ровно как в прототипе.** Цикл `products.map` заменён на три
запроса: `product.findMany` + `groupBy` по `[productId, confirmed]` для JTBD +
`groupBy` по `[productId, status]` для гипотез. Замер на реальных данных
(27 продуктов, тот же счётчик операций через Prisma-middleware):

```
old: ops=82  16.1ms     (1 + 3×27 — ровно линейно, как и предсказано)
new: ops= 3   1.8ms     [Product.findMany, JTBD.groupBy, Hypothesis.groupBy]
correctness: IDENTICAL
```

Число операций теперь **не зависит** от количества продуктов. Per-product
хелперы (`getJtbdCoverage`, `getHypothesisStatusCounts`) не тронуты — они
правильной формы для вызова про один продукт и используются так в других
местах. Нулевой случай (продукт без JTBD и гипотез) не даёт строк в `groupBy`
вообще, поэтому проставляется явно; на это добавлены три интеграционных теста,
включая «счётчики не перетекают между продуктами» — единственный правдоподобный
баг такой переписки, которого тест на одном продукте не поймал бы.

**Проверено попутно: других N+1 в слое метрик не осталось.** Обход всех
`lib/*.ts` на предмет запроса внутри цикла или `map(async …)` даёт только
`getRoadmapStatusByProduct`, и там уже `groupBy` + один `findMany`, а цикл —
в памяти.

**A3 не включено, и это решение по данным, а не по вкусу.**

После A2 замерена стоимость именно тех страниц, ради которых кэш и
предлагался:

```
TOTAL /cpo               ops= 14  16.9ms
TOTAL /reports/gaps      ops=  4  10.4ms
TOTAL метрики дашборда   ops=  8   6.8ms
```

Все три — с фиксированным числом операций, не растущим по числу продуктов.
То есть экономить кэшу нечего: речь о ~17 мс на самой тяжёлой агрегатной
странице.

Что стоит с другой стороны: в проекте **0** использований `unstable_cache` и
`revalidateTag` против **219** вызовов `revalidatePath` в 26 файлах экшенов.
Инвалидация написана под кэш маршрутов (путями), а `unstable_cache` живёт на
тегах — это разные механизмы, и опираться на их частичное пересечение как на
несущую конструкцию нельзя без проверки каждой из 219 точек. Практически
включение кэша означает завести теги и добавить `revalidateTag` по всем 26
файлам, где **один пропуск даёт устаревшие числа**.

И вот это решает: устаревшие числа здесь — не мелкое неудобство. Весь продукт
про то, «что подтверждено» и «чего не хватает»; отчёт о пробелах, который
показывает пробел закрытым, вреднее медленного отчёта. Менять 17 мс на такой
класс ошибок — плохая сделка.

**Что изменит решение.** Если появится страница с растущим по данным числом
запросов, или реальная жалоба на скорость, или мультиарендность (когда
агрегаты станут считаться на порядок больших объёмах) — вернуться к A3, начав
с тегов на самих агрегатных функциях. Замеры выше воспроизводятся тем же
скриптом-счётчиком, чтобы решение можно было пересмотреть на новых числах, а
не на ощущениях.

### A4. ◑ Дыра закрыта, дедупликация отложена. 12 почти одинаковых `updateXField`

`updateFeatureField`, `updateInsightField`, `updateJtbdField` и ещё 9 — один и
тот же скелет: `switch` по имени поля, `trim()`, проверка на пустоту,
`prisma.X.update({ where: { id } })`, два `revalidatePath`, `return { ok: true }`.

Важно: **дублирование и дыра в безопасности здесь — одна и та же проблема.**
Не «отрефакторить, а потом ещё и починить доступ», а «общий защищённый
хелпер чинит оба разом». Это делает A1 существенно дешевле, чем 64 точечные
правки.

### A5. ✅ Сделано. Один тест изоляции на 179

Единственная во всём наборе проверка «действие не трогает чужие данные»:

```
tests/integration/actions/departments.test.ts:117
  it('does not move a product belonging to a different user', ...)
```

Она существует, потому что `assignProductsToDepartment` — одно из немногих
действий, которое реально фильтрует по `userId`. То есть **нужный паттерн
теста в репозитории уже есть**, просто применён к 1 действию из 64+. Ничего
изобретать не нужно — нужно обобщить существующее.

## B. UX / доступность

### B1. ✅ Сделано. 20 страниц из 75 не имеют `<h1>`

Измерено обходом всех `page.tsx` + проверкой в браузере: `/hypotheses`,
`/products`, `/segments`, `/features`, `/jtbd/graph` и ещё 15 отдают документ,
в котором заголовочная структура начинается с `<h2>`.

Причина одна и чинится в одном месте — `components/shared/section-heading.tsx`
жёстко зашивает уровень:

```tsx
export function SectionHeading({ title, description }) {
  return <div ...><h2 className="text-xl font-bold">{title}</h2>...</div>
}
```

Он используется как **заголовок страницы** на 14 страницах. Достаточно
добавить проп уровня (по умолчанию `h2`, чтобы ничего не сломать) и передать
`level={1}` в местах, где это заголовок страницы.

### B2. ✅ Сделано. Kanban-доска недоступна с клавиатуры

Замер в браузере на `/hypotheses`:

```
draggable=5  focusable=0  role=0
```

Карточка гипотезы — это `<div draggable onClick={...}>` без `tabIndex`, без
`role`, без `onKeyDown`. С клавиатуры её нельзя ни открыть, ни перевести в
другой статус. Скринридер не объявит её интерактивной.

**Решение уже есть в этом же репозитории.** Фаза 6 (`2.0-ux-improvement-plan.md`)
столкнулась ровно с этой проблемой на диаграмме Ганта и решила её правильно:
рядом с каждой полосой — настоящая `<a>`-ссылка на форму редактирования,
скрытая через `opacity`, а не `display:none`, поэтому остаётся в таб-порядке.
Тот же приём переносится на kanban и на сетку виджетов дашборда
(`dashboard-widget-grid.tsx`, та же проблема).

### B3. ✅ Сделано. Нет skip-link — ~12 табов до контента на каждой странице

Проход табом по `/pm` даёт 12 остановок подряд по навигации, прежде чем
фокус доходит до содержимого:

```
1. RPM.  2. Продукты  3. Фичи  4. Конкуренты  5. Люди  6. Департаменты
7. Сегменты  8. Исследования  9. Гипотезы  10. Разговоры  11. Инсайты  12. Маркетинг
```

Ссылки внутри hover-подменю участвуют в таб-порядке всегда, даже когда меню
закрыто. Плюс поиск и переключатель персон. Стандартное решение —
`<a href="#main" class="sr-only focus:not-sr-only">` первым элементом в
`layout.tsx` и `id="main"` на `<main>`; попутно стоит убрать закрытые подменю
из таб-порядка.

### Фаза 3 — как сделано

**B1.** У `SectionHeading` появился проп `level` (по умолчанию `2`, чтобы ни
одно существующее использование как заголовка секции не изменилось), и на 15
страницах, где он служит заголовком страницы, передан `level={1}`. Размер
шрифта одинаков на обоих уровнях: правка семантическая, страницы выглядят
ровно как раньше. Проверено запросом HTML со всех 17 страниц: на каждой ровно
один `<h1>`, и структура заголовков начинается именно с него.

**B2, kanban.** Формулировка гипотезы стала настоящей `<Link>`, а рядом
появилась ссылка «Изменить статус» на форму — скрытая через `opacity`, а не
`display:none`, поэтому остаётся в таб-порядке (тот же приём, что у диаграммы
Ганта). Обе ссылки останавливают всплытие, чтобы клик мышью по карточке
по-прежнему давал ровно один переход. Замер до: `draggable=5 focusable=0`.
После: 9 карточек из 9 содержат фокусируемый элемент и ссылку на форму.

**B2, сетка виджетов.** Здесь ссылка не помогает: перетаскивание **и есть**
действие, а не способ куда-то попасть. Поэтому к каждой строке добавлены
кнопки «выше»/«ниже» с `aria-label`; у крайних строк соответствующая кнопка
`disabled`, а не молча ничего не делает. Мышиный путь не тронут. Проверено:
порядок меняется и сохраняется в `localStorage`.

**B3.** `<a href="#main" class="sr-only focus:not-sr-only">` первым элементом
в `layout.tsx` плюс обёртка `<div id="main" tabIndex={-1}>` вокруг `children`
— одна обёртка вместо `id` на 73 страничных `<main>`: цель должна
существовать один раз и не может рассинхронизироваться при добавлении новой
страницы. `tabIndex={-1}` обязателен — без него часть браузеров прокручивает
к якорю, но оставляет фокус в навигации, и следующий Tab продолжает с шапки.

**Осознанно не сделано из формулировки B3: подменю не убраны из таб-порядка.**
Ссылки внутри закрытых подменю действительно добавляют остановок, но меню
раскрывается по `group-focus-within` — то есть с клавиатуры оно уже работает
правильно, и удаление ссылок из таб-порядка **сломало бы** единственный
клавиатурный путь к Фичам, Конкурентам, Людям и Департаментам. Правильное
решение — превратить пункт в disclosure-кнопку с `aria-expanded`, это отдельная
работа. Skip-link решает исходную жалобу («долго идти до контента»), ничего не
ломая: замерено 21 остановка до контента без него (в плане было 12 — с тех пор
в шапке прибавилось пунктов), с ним — одна.

**Побочная находка, исправлена здесь же.** `getNavStage` (C1) вызывается в
**корневом** layout, и когда база данных оказалась недоступна, исключение из
него положило **все** маршруты сразу: 500 без навигации на каждой странице.
Стадия меню — настройка отображения и не должна иметь такой власти; теперь при
ошибке она возвращает `'full'`, то есть отказывает в безопасную сторону,
ничего не скрывая.

Покрытие: 4 E2E (по одному на каждый пункт плюс проверка, что первая строка
списка виджетов не двигается вверх).

### B4. Удаление не показывает масштаб разрушения

`components/shared/delete-button.tsx` — нативный `confirm('Удалить
безвозвратно?')`. В схеме **38 связей с `onDelete: Cascade`**. Замер по
сид-данным, сколько строк уносит одно нажатие:

```
Рутокен CLM   →  41 прямая дочерняя запись
   segments 9, jtbds 6, hypotheses 5, researches 4, features 4,
   conversations 3, rtbs 3, insights 3, competitors 2, productResources 2
   (+ косвенные: HypothesisStatusChange, JtbdSequenceEdge,
      CompetitorNewsItem, ProcessStep, ProcessEdge, ActionPlan)
```

Пользователь видит одну строку без единой цифры, отменить нельзя. Минимальное
и честное исправление — посчитать зависимые записи перед удалением и показать
их в диалоге («Будет удалено: 9 сегментов, 6 JTBD, 5 гипотез…»). Это не
требует ни undo-механики, ни soft-delete — только запрос `_count` и нормальный
диалог вместо `confirm()`.

## Фазы

Порядок — по убыванию риска, а не по объёму работы. Фазы 1–2 независимы от 3–5.

**Фаза 1. ✅ Сделано. Защищённый слой мутаций (A1 + A4 + A5).**
Общий хелпер вида `assertOwned(model, id, userId)` / обёртка над мутацией,
через которую проходят все 64 действия; общий `updateEntityField`, снимающий
12 дублей. К каждому семейству действий — тест изоляции по образцу
`departments.test.ts:117`. Критерий готовности: попытка мутировать чужую
запись падает, и это зафиксировано тестом для каждого модуля, а не для одного.
Делать **до** любого включения реальных сессий.

**Фаза 2. ✅ Сделано. Фильтрация чтений, оставшихся без `userId`.**
Точечно: `lib/team-workload.ts` (`processStep`, `productTeamMember`) и
ревизия остальных запросов, которые полагаются на «`productId` уже проверен».
Дёшево, но должно идти сразу за Фазой 1, иначе картина безопасности остаётся
наполовину починенной.

### Фазы 1–2 — как сделано

**Общий примитив — `lib/ownership.ts`.** Таблица из 21 модели: для каждой
запрос, доказывающий, что запись принадлежит пользователю. Пятнадцать моделей
проверяются напрямую по `userId`, остальные шесть — только по цепочке связей
(`processStep → process → product → user` и т.п.), ровно той же, по которой
они и живут без собственного `userId`. Никакого `any`: каждая запись таблицы
типизирована отдельно, поэтому TypeScript проверил все цепочки — опечатка в
имени связи не собралась бы.

**Почему проверка отдельным запросом, а не `where: { id, userId }`.** У Prisma
`update`/`delete` требуют **уникальный** селектор, а `userId` не входит ни в
один уникальный индекс — расширить фильтр просто нельзя. `updateMany` принял
бы его, но молча завершается успехом на нуле строк, то есть скрывает ровно тот
случай, ради которого всё и делается.

**Две формы, по типу возврата экшена.** `denyUnowned` возвращает ошибку тем
экшенам, у которых есть канал для ошибки; `assertOwned` поднимает 404 тем,
которые редиректят и канала не имеют. 404, а не «доступ запрещён»: для того,
кто записью не владеет, её и правда не существует, а «запрещено» подтвердило
бы, что такой id есть.

**Покрытие — все мутации, а не большинство.** Итог обхода: из мутирующих
экшенов без проверки остались ровно три — `createProduct`, `createDepartment`,
`createPerson`, и это правильно: они создают запись верхнего уровня и сами
проставляют `userId: getCurrentUserId()`, владельца проверять не у чего.

Отдельно разобраны случаи, где одной проверки мало:

- **Рёбра** (`createJtbdSequenceEdge`, `createProcessEdge`) проверяют **оба**
  конца: ребро — это запись, трогающая две сущности, и проверки только
  источника хватило бы, чтобы привязать чужую цель.
- **Пакетные записи раскладки** (`saveJtbdGraphPositions`,
  `saveProcessStepPositions`) проверяют **каждый** id из пакета: это массовая
  запись, целиком управляемая идентификаторами с клиента.
- **Создание из формы** (13 экшенов) проверяет продукт из `parsed.data`, а не
  из аргумента — продукт там приходит из формы клиента.

**A5.** `tests/integration/ownership.test.ts` строит два «мира» — по продукту
со всей обвязкой на каждого из двух пользователей — и прогоняет по всем 21
модели: свою запись видно, чужую с тем же кодом нет. Отдельный тест на шесть
моделей без собственного `userId`, у которых вся защита — цепочка связей и
поэтому её проще всего незаметно сломать. Плюс проверка, что текст ошибки —
«не найдено», а не «запрещено».

**Фаза 2.** В `lib/team-workload.ts` два запроса фильтровались только по
`productId`, хотя `userId` в функцию передавался: `processStep` и
`productTeamMember`. Добавлена связь до владельца. Обход всех `lib/*.ts` на
тот же шаблон («фильтр по productId, userId нигде в `where`») больше не даёт
ни одного совпадения.

**A4 — дыра закрыта, дедупликация сознательно отложена.** Аргумент плана был в
том, что дублирование и дыра в безопасности — одна проблема, и общий хелпер
чинит обе. На практике безопасность закрылась иначе: все 12 `updateXField`
получили тот же guard, что и остальные 80 экшенов, то есть единообразно, а не
особым механизмом на 12 функций. После этого от A4 остаётся чистая
косметическая дедупликация двенадцати `switch`-блоков — реальная, но заметно
менее ценная, и делать второй большой механический рефакторинг тех же файлов в
том же коммите значит умножать риск ради читаемости. Вынесено как отдельная
необязательная задача; на безопасность она больше не влияет.

**Фаза 3. ✅ Сделано. Доступность (B1 + B2 + B3).**
Три независимых пункта, все с уже существующим в репозитории образцом решения:
проп уровня у `SectionHeading`, ссылка-эскейп по образцу Фазы 6 для kanban и
сетки виджетов, skip-link в `layout.tsx`. Самая заметная польза на единицу
усилий; ничего не ломает.

**Фаза 4. ✅ Сделано (A2), A3 закрыт по данным.**
Сначала A2 — замена уже прототипирована и проверена на идентичность, риск
низкий. Затем осторожно A3: начать с чисто агрегатных страниц (`/cpo`,
`/reports`), где `revalidatePath` уже расставлен, и не трогать страницы с
инлайн-редактированием, пока не будет уверенности в инвалидации.

**Фаза 5. Диалог удаления (B4).**
Замена `confirm()` на нормальный диалог с подсчётом зависимых записей.
Отдельно и последней, потому что это единственный пункт, требующий новый
UI-компонент, а не правку существующего.

**Ритуал по каждой фазе** — тот же, что и во всех предыдущих:
`npm run lint && npm run typecheck` → unit → integration → E2E → скриншоты →
обновление документации → коммит → push в `origin/2.0`.

## Что намеренно не предлагается

- **Мультиарендность как продуктовая функция** (воркспейсы, приглашения,
  роли). Фаза 1 — про то, чтобы существующая однопользовательская модель была
  корректной, а не про новую модель доступа. `PersonaSwitcher` по-прежнему не
  является границей доступа и не должен ей становиться в рамках этого плана.
- **Замена ручного `where: { userId }` на middleware/RLS.** Обсуждаемо, но это
  архитектурное решение другого масштаба; Фаза 1 совместима с обоими путями и
  не закрывает ни один из них.
- **Мобильная адаптация** — вне рамок по решению пользователя.
- **Soft-delete / undo** — B4 решается показом масштаба, полноценная отмена
  удаления это отдельная большая фича.
