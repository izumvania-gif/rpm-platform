# UX-аудит и план улучшений 2.0-представлений

## Контекст

Прямой запрос: «this is a big block of functional, right now most of it is
not very much logical or user-friendly. Need a big UX audit» — плюс три
конкретных пункта, вошедших в аудит как обязательные к решению:

1. PM-хаб должен показывать карточку продукта, а не только роадмап/команду/
   процессы — **решено с пользователем**: блок с полями продукта
   встраивается прямо в `/pm` (не просто ссылка на `/products/[id]`).
2. Нужно уметь добавлять человека прямо как PM, «привязывая» его к текущему
   продукту — **решено с пользователем**: это новый ростер команды продукта
   (Person ↔ Product many-to-many), а не просто назначение
   `Product.ownerId`.
3. Кнопка «Добавить процесс» иногда «улетает наверх экрана» — воспроизведено
   и диагностировано ниже, это не одна, а две разных причины.

Аудит охватывает весь функционал, добавленный по
`plans/platform-views-plan.md` (`/pm`, `/cpo`, `/public`, `/marketing-hub`,
`/sales-hub`, `/people`, `/departments`) — ровно тот «большой блок
функционала», о котором идёт речь. 1.0-модули (Продукты, Сегменты,
Исследования и т.д.) в аудит не входят — они уже прошли отдельный
UX-ретест перед релизом 1.0 (`plans/ui-improvement-plan.md`).

## Методология

Живой прогон каждого раздела в браузере под пятью линзами — PM,
CPO, маркетинг, продажи, внешний посетитель (`/public`) — с конкретными
задачами («добавь человека в команду», «посмотри, что можно сказать
сегменту N», «проверь, есть ли фича X»), а не абстрактный просмотр
страниц. Два визуальных бага ниже — не предположения, а воспроизведены
скриптом с фиксацией `scrollY` и скриншотами до/после.

## A. Подтверждённые баги (не про вкус — про то, что сломано)

### A1. «Добавить процесс» улетает наверх экрана — причина 1: настоящий баг рендера

Когда у только что созданного процесса ещё нет ни одного шага,
`components/process-graph/canvas.tsx` рендерит `<AddStepPanel>` (кнопка
«+ Добавить шаг») **вне** `<ReactFlow>` — просто как соседний элемент
внутри центрированного flex-блока:

```tsx
{nodes.length === 0 ? (
  <div className="flex h-full flex-col items-center justify-center ...">
    <p>...</p>
    <AddStepPanel processId={processId} people={people} stepCount={steps.length} />
  </div>
) : (
  <ReactFlow ...>
    ...
    <AddStepPanel .../>  {/* здесь всё нормально — есть контекст ReactFlow */}
```

`AddStepPanel` внутри себя рендерит `<Panel position="top-left">` из
`@xyflow/react` — а `Panel` спроектирован работать **только** внутри
`<ReactFlow>`/`<ReactFlowProvider>`, чей `.react-flow`-контейнер даёт ему
`position: relative` как точку отсчёта. Без этого контейнера `Panel`
позиционируется абсолютно относительно ближайшего спозиционированного
предка — а такого предка на пути вверх по дереву нет вообще, поэтому
браузер абсолютно позиционирует его от **окна целиком**. Результат
воспроизведён скриншотом: кнопка «+ Добавить шаг» рисуется в самом
верхнем левом углу окна браузера, **поверх** красной полосы и `SiteNav`
— визуально «улетевшая на самый верх экрана», причём только пока в
процессе 0 шагов (после первого шага `AddStepPanel` уже внутри
`<ReactFlow>` и ведёт себя нормально).

**Фикс (реализовано в Фазе 1).** Второй вариант — форма вынесена в
отдельный `AddStepForm` без `<Panel>`-обёртки, используется напрямую в
пустом состоянии (обычная кнопка/форма в потоке flex-блока); `AddStepPanel`
(с `<Panel>`) остаётся только для случая внутри `<ReactFlow>`. Подтверждено
скриншотом того же репро-скрипта: кнопка теперь рисуется по центру карточки
процесса, а не поверх шапки сайта.

### A2. «Добавить процесс»/«Добавить план»/«Добавить пункт» — причина 2: сброс скролла

`/pm` — одна длинная страница (Роадмап → Команда → Экшн-планы → Процесс).
Каждое «Добавить X» — переход на отдельную страницу (`/pm/roadmap/new`,
`/pm/action-plans/new`, `/pm/processes/new`), а после сохранения —
обычный `redirect()` обратно на `/pm?productId=...`. Обычная
серверная навигация в браузере **всегда** возвращает скролл к началу
страницы (`scrollY: 0` подтверждено скриптом), даже если пользователь
до этого проскроллил вниз до секции «Процесс» (например, `scrollY: 656`
на середней по размеру странице — на реальных данных с полным роадмапом
и командой может быть в разы больше). Пользователь физически видит,
что «всё прыгнуло наверх» — секция, где он только что работал, теперь
на 2–3 экрана ниже видимой области.

Это не единичный баг «Процесса» — та же механика у **всех** «Добавить X»
на `/pm`, просто тем заметнее, чем ниже секция: у Роадмапа (первая секция)
почти незаметно, у Экшн-планов уже раздражает, у Процесса (последняя
секция) — максимально дезориентирует, что и заметил пользователь именно
на нём.

**Фикс (реализовано в Фазе 1).** Изначально предполагался редирект на
`#section`-якорь — не сработало: тестирование показало, что
`redirect()` из Server Action в Next.js 14 **полностью отбрасывает hash
из URL** (не проблема скролла конкретно, сам fragment ни разу не долетает
до браузера — подтверждено логом `framenavigated`). Реализованный фикс —
query-параметр `scrollTo` вместо hash (query-строка редиректом не
теряется, в отличие от hash): `/pm?productId=X&scrollTo=process` и т.п.,
плюс маленький клиентский компонент `components/shared/scroll-to-section.tsx`
(`ScrollToSection`), который на маунте читает `id` из пропа (сервер уже
читает `searchParams.scrollTo` — страница `/pm` и так Server Component с
`searchParams`, доп. `useSearchParams()`/`Suspense` не понадобились) и
вызывает `document.getElementById(id)?.scrollIntoView()`. Подтверждено
живым репро-скриптом: `scrollY` после редиректа — не `0`, а положение
секции «Процесс». Более глубокое решение (инлайн-формы/модалки прямо на
`/pm` без ухода со страницы, как уже сделано для `createXQuick` на других
канвасах) — Фаза 5 плана ниже, дороже, но полностью убирает переход
между страницами для всех «мелких» добавлений.

### A3. Мастер настройки продукта: чекбоксы сегментов/связей сбрасываются после каждого добавления

В шаге JTBD мастера (`components/onboarding/jtbd-step-form.tsx`) и в шаге
Фичи и RTB (`components/onboarding/features-step-form.tsx`, дважды — для
чекбоксов JTBD и чекбоксов Features) после каждого `submit()` состояние
выбранных чекбоксов явно обнуляется:

```tsx
setJtbds((prev) => [...prev, { ...result.jtbd, segments: jtbdSegments }])
setTitle('')
setCategory('')
setSegmentIds([])   // ← сбрасывает выбранные сегменты при каждом добавлении джоба
setError(null)
```

При типичном сценарии — один и тот же продукт, тот же набор из 2–3
сегментов, несколько джобов подряд («Sync для сегмента X», «Onboarding
для Y», ...) — пользователь вынужден заново кликать одни и те же
чекбоксы после каждого сохранения. Ровно то, о чём сообщил пользователь:
«its not convenient to always click on the segments when adding jobs».

То же самое дублируется в шаге Фичи и RTB: `featureJtbdIds` (какие JTBD
закрывает фича) и `rtbFeatureIds` (на какие фичи опирается RTB) — оба
чекбоксовых списка сбрасываются той же строкой в
`submitFeature()`/`submitRtb()`.

Показательно, что в том же мастере уже есть правильный пример: шаг
Гипотез (`components/onboarding/hypotheses-step-form.tsx`) использует
`<Select>` для `jtbdId`/`segmentId` и **не** обнуляет их после
`submit()` — паттерн «оставить выбор для следующего добавления» уже
реализован в кодовой базе, просто не для чекбоксовых списков.

**Фикс (реализовано в Фазе 1):** убраны `setSegmentIds([])`/
`setFeatureJtbdIds([])`/`setRtbFeatureIds([])` из трёх мест. Раз выбор
больше не сбрасывается автоматически, пользователю нужен способ снять
чекбокс, если сегмент/связь больше не подходит для следующей записи —
сам чекбокс это уже даёт (повторный клик снимает галочку), поэтому
дополнительного UI не потребовалось.

## B. Найденные сопутствующие проблемы

- **Шапка `DashboardWidgetCard` не адаптируется под мобильный экран.**
  `flex flex-row items-center justify-between` без `sm:`-варианта — на
  390px кнопка действия («Добавить план» и т.п.) зажимается в узкую
  колонку рядом с многострочным описанием, которое переносится текстом
  вокруг неё (скриншот `mobile-pm-list.png`). Не то же самое, что уже
  задокументированное ограничение «нав-бар не сворачивается в гамбургер»
  — это отдельная, более мелкая, но регулярно всплывающая проблема
  именно у 2.0-карточек (`DashboardWidgetCard` используется на `/pm`,
  `/cpo`, `/public`, `/marketing-hub`, `/sales-hub` — везде одна и та же
  вёрстка шапки).
- **Ни у одной формы «Добавить X» на `/pm` нет кнопки «Отмена».**
  Работает и в 1.0 (не новая проблема сама по себе), но на `/pm` она
  ощутимее из-за А2 выше — единственный способ передумать и вернуться,
  не сохраняя, это браузерная кнопка «Назад», и результат не всегда
  предсказуем (может увести на несколько шагов назад по истории, а не
  ровно на `/pm`).
- **Секция «Команда» — только производная, без собственного состояния.**
  Список строится исключительно из того, у кого уже есть назначенный
  пункт роадмапа или шаг процесса (`lib/team-workload.ts`) — курица и
  яйцо: чтобы человек появился в «Команде», его сначала нужно
  где-то назначить, а чтобы его назначить (например, выбрать
  ответственного в форме пункта роадмапа), он уже должен существовать в
  `/people`. Нет способа сказать «эти три человека — моя команда на этом
  продукте» заранее, до того как появится первая задача. Это ровно то,
  что просил пользователь (ростер) — решение в Фазе 2 ниже.
- **PM не может создать нового человека, не покидая `/pm`.** Единственный
  способ — уйти на `/people/new`, создать, вернуться на `/pm`, заново
  выбрать продукт. `Person` осознанно не имел inline-create раньше
  («nothing inline-creates a person yet, add it when a real picker needs
  it» — `CLAUDE.md`), но ростер команды продукта — ровно тот реальный
  picker, который это оправдывает.
- **`/pm` не показывает вообще ничего о самом продукте.** Заголовок
  страницы — буквально «PM» и статичное описание хаба, а не название/
  стадия/описание продукта. Человек, открывший `/pm` впервые (или после
  переключения продукта), не видит подтверждения «да, я сейчас смотрю
  на продукт X, вот что это за продукт» без ухода на `/products/[id]`.
  Решение — часть требования №1 пользователя, Фаза 2 ниже.
- **`/cpo` — тоже одна бесконечно длинная страница**, тот же паттерн, что
  у `/pm`, только секций 4 (Продукты / Экосистема / Ключевые направления /
  Мультипродуктовый роадмап) и первая секция (сетка продуктов) сама по
  себе может быть длиннее экрана при десятках продуктов — тогда все
  остальные секции уходят далеко вниз без якорей/оглавления, чтобы
  быстро туда попасть.
- **На `/cpo` нет способа массово привязать продукты к департаменту.**
  Присвоить департамент можно только по одному продукту за раз (через
  форму/инлайн-поле самого продукта) — если только что завели департамент
  «IoT-безопасность» и под него нужно перевести 5 существующих продуктов,
  это 5 отдельных заходов на страницу каждого продукта.
- **Список продуктов на `/cpo` не фильтруется и не ищется** — при большом
  количестве продуктов (сейчас в демо-данных не проблема, но при росте
  каталога) сетку из 30+ карточек, разбитую по департаментам, придётся
  долго проматывать, чтобы найти один конкретный продукт.
- **Выпадающий список сегментов на `/marketing-hub` — плоский, с
  префиксом продукта в каждой опции**, а не сгруппированный по продукту
  (`<optgroup>`). При нескольких продуктах с 3–4 сегментами каждый список
  быстро становится длинным текстовым месивом вида «Продукт А —
  Enterprise», «Продукт А — SMB», «Продукт Б — Enterprise»…
- **Переключатель продукта на `/pm` и `/sales-hub` не даёт создать новый
  продукт прямо оттуда** — только выбор из уже существующих; если у PM
  ещё нет ни одного продукта, есть аккуратная заглушка со ссылкой, но
  если хотя бы один уже есть, добавить второй без ухода на `/products/new`
  нельзя.

## C. Мастер настройки продукта: аудит с учётом 2.0

Отдельный запрос — проверить, насколько мастер настройки
(`/products/[id]/onboarding/*`) учитывает то, что появилось в 2.0. Ответ,
подтверждённый чтением кода: никак.

- `components/onboarding/wizard-steps.ts` перечисляет ровно 6 шагов —
  Сегменты → JTBD → Исследования → Гипотезы → Конкуренты → Фичи и RTB —
  все они 1.0. Ни Люди, ни Департамент нигде не упоминаются.
- `app/products/[id]/onboarding/done/page.tsx`, финальный экран
  мастера, показывает чек-лист заполненности ровно по тем же 9 типам
  1.0-контента (Сегменты, JTBD, Исследования, Разговоры, Инсайты,
  Гипотезы, Конкуренты, Фичи, RTB) — с количеством и ссылкой
  «заполнить/изменить» на каждый. Ни слова о команде продукта.

Итог: продукт, только что созданный через мастер, всегда стартует без
единого человека в команде — PM, дошедший до конца мастера и открывший
`/pm`, сразу попадает в ситуацию «курица и яйцо» из раздела B (пустая
секция «Команда»), хотя мастер — ровно то место, где естественно один
раз перечислить, с кем работаешь над этим продуктом.

**Предложение: новый шаг «Люди» в мастере**, между Конкурентами и Фичи
и RTB (порядок не принципиален — можно и последним перед Done; главное —
не первым, чтобы не заставлять думать о команде раньше, чем о самом
продукте).

- Ключ шага — `'people'`, добавляется в `WIZARD_STEPS`
  (`wizard-steps.ts`) с меткой «Люди».
- Форма (`components/onboarding/people-step-form.tsx`, по образцу
  остальных степ-форм) — тот же паттерн, что предлагается для ростера в
  Фазе 2 плана ниже: выбрать существующего человека из `/people`
  (`<Select>`) **или** создать нового прямо в форме (имя + роль), в
  обоих случаях сразу привязывая его к текущему продукту через
  `ProductTeamMember` (модель из Фазы 2 — этот шаг мастера физически не
  может быть реализован раньше неё, зависимость явная).
- Понадобится `createProductTeamMemberQuick`-вариант в новом
  `lib/actions/product-team.ts` (создаётся вместе с моделью в Фазе 2),
  не отдельный action только под мастер.
- Список уже добавленных людей рендерится тем же `<WizardEntryList>`,
  что и остальные шаги — единообразие, не новый компонент.
- `done/page.tsx` — добавить десятую строку чек-листа «Команда»
  (счётчик участников, ссылка «заполнить/изменить»).

**Реализовано в Фазе 3** — почти как описано, с двумя уточнениями по
факту реализации: (1) вместо одного `createProductTeamMemberQuick`
переиспользованы оба узких экшена из Фазы 2
(`addProductTeamMemberQuick`/`createPersonAndAddToTeamQuick`) — два
разных пути добавления (выбрать/создать) естественно требуют разных
аргументов, один экшен с веткой внутри не упростил бы код; (2) ссылка
чек-листа ведёт на сам шаг мастера (`/products/[id]/onboarding/people`),
как и все остальные девять строк, а не на `/pm` — при написании этого
раздела шаг мастера ещё не был спроектирован, а раз он появился,
единообразие с остальным чек-листом важнее, чем вести сразу на итоговое
представление ростера.

**Департамент — сознательно не добавляется в мастер.** Это атрибут
продукта в целом (`Product.departmentId`), не то, что имеет смысл
заполнять в потоке быстрого онбординга одного продукта — уже есть
инлайн-редактируемое поле на `/products/[id]` (и предлагается в блоке
продукта на `/pm`, Фаза 2 плана ниже), этого достаточно. Дублировать его
в мастере — лишний шаг для сценария, где департаменты часто ещё даже не
заведены (сам мастер обычно и запускается для самого первого продукта).

## D. Интерактивная диаграмма Ганта (вдохновение — Confluence Roadmap)

Сейчас `components/roadmap-gantt/gantt-chart.tsx` — чистый серверный
компонент, буквально без единого обработчика событий (в файле есть
собственный комментарий об этом: «Server-renderable, no client state —
the only interactivity is a native `title` hover tooltip»). Позиции и
ширины полос — проценты, посчитанные один раз на сервере
(`percent(date, rangeStart, rangeEnd)`), подписи — эвристика по числу
символов (`labelFitsInBar`), без реального замера DOM. Единственное
взаимодействие — наведение мышью показывает нативный тултип с полным
названием и датами; редактирование дат/статуса возможно только через
обычную форму пункта роадмапа, полностью в стороне от самой диаграммы.

Запрошено: сделать диаграмму редактируемой прямо в канвасе —
«make the gant chart editable and make the user be able to move the
roads» — по образцу Confluence Roadmap Planner (перетаскивание полос и
их краёв прямо на таймлайне).

### Предлагаемая модель взаимодействия

- **Перетащить тело полосы** — переносит весь диапазон (обе даты) на ту
  же длительность, не меняя её. Курсор `grab`/`grabbing`, полоса
  визуально «прилипает» к сетке дней при отпускании (не к произвольному
  пикселю — иначе даты будут не выровнены на полночь).
- **Перетащить левый/правый край полосы** — меняет только `startDate`
  или только `endDate` (изменение длительности), с той же привязкой к
  дню. Явный `cursor: ew-resize` на 6–8px зоне у каждого края.
- **Перетащить полосу по вертикали на другой трек** — переносит пункт
  роадмапа в другую дорожку (`track`/`trackGroup`) простым drop на
  строку другого трека. **Только на `/pm`** (один продукт — треки
  осмысленные, это `RoadmapItem.track`); на `/cpo`, где трек — это целый
  продукт (`getMultiProductGanttLayout()`), вертикальное перетаскивание
  не имеет смысла и не реализуется там вовсе.
- **Перетащить веху (milestone)** — переносит дату метки с той же
  привязкой к дню.
- Все операции — **optimistic UI**: полоса визуально двигается сразу по
  ходу перетаскивания (пересчёт `left`/`width` в процентах на клиенте,
  та же формула `percent()`, что уже есть на сервере, но теперь
  вызывается и в браузере), запрос на сохранение уходит по `pointerup`,
  а не на каждый `pointermove`; если сервер отклонит (валидация:
  `endDate` не раньше `startDate` и т.п.), полоса откатывается на
  исходную позицию с текстом ошибки.

### Технический подход

- `GanttChart` становится клиентским компонентом (`'use client'`) —
  архитектурный разворот относительно исходного дизайна, явно
  зафиксированного в комментарии файла как «no client state». Серверная
  часть (`app/pm/page.tsx`/`app/cpo/page.tsx`) продолжает считать
  `buildGanttLayout()`/`getMultiProductGanttLayout()` на сервере и
  передаёт готовый `GanttLayout` пропом — сама раскладка (группировка по
  трекам, диапазон дат) не переезжает на клиент, меняется только рендер
  полос.
- Перетаскивание — через нативные Pointer Events
  (`onPointerDown`/`onPointerMove`/`onPointerUp` с
  `setPointerCapture`), не отдельная drag-and-drop библиотека — та же
  философия, что уже используется в kanban-доске гипотез (нативный HTML5
  DnD) и в `@xyflow/react`-канвасах (свой обработчик перетаскивания
  узлов): не тянуть новую зависимость под drag, если можно на нативных
  событиях.
- Пересчёт даты из пикселей перетаскивания: `deltaPx → deltaPercent
  (относительно ширины чарта) → deltaMs (percent * (rangeEnd -
  rangeStart)) → новая дата`, затем округление до начала дня
  (`startOfDay`, `date-fns` уже в зависимостях).
- Новый узкий экшен `updateRoadmapItemDates(id, startDate, endDate,
  track?)` в `lib/actions/roadmap.ts` (не полный `updateRoadmapItem` —
  отдельный экшен под drag-сценарий, сохраняет только три поля, без
  прогона через Zod-схему формы редактирования целиком). Тот же экшен
  обслуживает и полосы, и вехи — веха это `RoadmapItem.isMilestone`, не
  отдельная модель.
- E2E-покрытие через Playwright `mouse.move`/`mouse.down`/`mouse.up` (не
  `dragTo()` — тот рассчитан на HTML5 DnD, а тут Pointer Events, нужен
  ручной пошаговый мышиный жест).

### Осознанно не входит в первую версию

- **Undo/redo** — оптимистичный откат при ошибке сервера есть, но
  «отменить последнее успешно сохранённое действие» — нет, нужна история
  операций, слишком большая фича для этого захода.
- **Множественное выделение и групповое перетаскивание** — только одна
  полоса за раз.
- **Клавиатурный доступ к перетаскиванию** — реальный пробел
  доступности: Pointer Events не дают клавиатурной альтернативы «из
  коробки». Нужна либо видимая кнопка «Редактировать даты» рядом с
  полосой (открывает обычную форму — единственный путь для пользователей
  без мыши/тачпада), либо стрелочные хоткеи при фокусе на полосе —
  открытый вопрос дизайна Фазы 6 ниже, не блокирует остальную
  функциональность, но обязателен к решению до релиза этой фичи, не
  после.
- **Мобильный тач-драг** — диаграмма и так требует горизонтального
  скролла на мобильном (`overflow-x-auto`, `min-w-[900px]`); совмещать
  скролл-жест и drag-жест на touch-экране — отдельная, более тонкая
  задача (различать «скроллю» от «тащу»), не входит в первую версию — на
  мобильном полосы остаются доступны только на просмотр/тултип.

## Два структурных изменения (согласованы с пользователем)

**Блок продукта на `/pm`.** Прямо под селектором продукта — карточка с
теми же полями, что редактируются на `/products/[id]`: название (инлайн),
стадия (инлайн-select), описание (инлайн-textarea), департамент и
ответственный PM (инлайн-select, те же поля, что уже добавлены в
`/products/[id]` в §11), плюс компактная ссылка «Открыть карточку
продукта →» для тех, кому нужен полный набор 1.0-модулей (сегменты, JTBD,
конкуренты и т.д.) — не дублировать все десять секций `/products/[id]`
внутри `/pm`, только идентификационные поля, которые PM хочет видеть и
править, не покидая хаб.

**Ростер команды продукта.** Новая модель `ProductTeamMember` (или
прямая many-to-many таблица `Person` ↔ `Product`, без дополнительных
полей на первом шаге — роль/даты присоединения можно добавить позже, если
понадобится) — раз пользователь подтвердил именно это, а не просто смену
`ownerId`. Секция «Команда» на `/pm` показывает объединение: явно
добавленные в ростер люди (даже с нулём активных дел — решает проблему
«курицы и яйца») **плюс** те, у кого уже есть назначенный пункт
роадмапа/шаг процесса, но кто почему-то не в ростере (не даёт никому
незаметно потеряться из вида). Кнопка «+ Добавить в команду» открывает
инлайн-форму с двумя путями: выбрать существующего человека из
`/people` **или** создать нового прямо тут — оба варианта сразу
привязывают его к текущему продукту.

   Верификация: живой репро-скрипт со скриншотами (форма с кнопкой
   «Отмена», раскрытый селектор с «+ Новый продукт», якоря `/cpo`,

   захват сейчас, уточнение через редактирование потом», что и у любого

   (без удаления второго) уже документированный, повторяющийся паттерн

   page… there's a second non-redirecting variant»). Удаление означало
   бы также переписывать порядка 10 не связанных с Фазой 5 E2E-спеков

   `public-dashboard.spec.ts`, `sales-hub.spec.ts`,
   `pm-roadmap-gantt.spec.ts`), которые открывают `/pm/roadmap/new` и
   соседние страницы напрямую через `page.goto()` для не относящейся к
   Фазе 5 подготовки данных. Полные страницы остались как осознанный
   «люк для полной формы» (Гант-планирование, привязка к
   фиче/JTBD/шагу процесса, теги) — кнопка «Отмена» из Фазы 4 на них
   тоже осталась актуальной как раз для этого случая.

   Отдельно обнаруженный по ходу реализации нюанс: у процесса, в
   отличие от пункта роадмапа и экшн-плана, есть второй уровень (его
   канвас) — старый полностью-страничный `createProcess` после
   создания редиректил прямо в канвас нового процесса
   (`/pm?productId=X&processId=Y&scrollTo=process`). Простой
   `router.refresh()` (как у двух других инлайн-форм) оставил бы
   пользователя на списке процессов, а не в только что созданном. Чтобы
   не потерять этот переход, `AddProcessForm` вместо `router.refresh()`
   делает `router.push()` с `processId` нового процесса в URL и
   `scroll: false` (чтобы не срабатывал стандартный
   скролл-к-началу-страницы у `router.push`), используя тот же
   `scrollTo=process` + `ScrollToSection` механизм из Фазы 1.

   новых integration-тестов на три Quick-экшена (счастливый путь +
   отклонение пустого обязательного поля на каждый). `npm run lint &&

   dev-сервера — не регрессия) → `npm run build` — все зелёные.

Каждая фаза — по тому же ритуалу, что и все предыдущие: `npm run lint &&
npm run typecheck` → unit → integration → E2E → скриншоты (включая
мобильный вьюпорт для Фазы 1) → обновление документации → коммит → push
в `origin/2.0`. Для Фазы 6 дополнительно — E2E-сценарий с ручным

## Осознанно вне рамок

- Поиск по продуктам на `/cpo` (п. 11) — низкий приоритет, не блокирует
  текущий масштаб демо-данных; включён в план на будущее, не обязателен
  к реализации в первую очередь. (`<optgroup>` на `/marketing-hub`, п.
  12 — реализован в Фазе 4, см. выше.)
- Полноценное сворачивание навигации в гамбургер на мобильных — уже
  задокументированное, отдельное, более крупное ограничение
  (`PROJECT_STATE.md`), не входит в этот план.
- Роль/дата присоединения на `ProductTeamMember` — не добавляются, пока
  не появится конкретная причина (тот же принцип, что и у остального
  минимализма схемы в этом проекте).
- Полный редизайн `/products/[id]` или удаление его секций в пользу
  `/pm` — не рассматривается; `/pm` получает только идентификационный
  блок, полная страница продукта остаётся отдельной и нужной для
  1.0-модулей.
- Департамент как шаг мастера настройки — сознательно не добавляется,
  обоснование в конце раздела C: атрибут продукта целиком, а не
  пошаговый выбор в потоке онбординга.
- Ограничения первой версии диаграммы Ганта (undo/redo, множественное
  перетаскивание, мобильный тач-драг) — расписаны отдельно в конце
  раздела D; клавиатурная альтернатива перетаскиванию — единственный из
  этих пунктов, который не «вне рамок», а обязательное условие релиза
  Фазы 6.

## Ритуал проверки

Идентичен использовавшемуся во всех предыдущих фазах 2.0: `npm run lint &&
npm run typecheck` → `npm run test:unit` → `npm run test:integration`
(реальный Postgres) → `npm run test:e2e` (headless Chromium,
`PLAYWRIGHT_CHROMIUM_PATH` обязателен в этом окружении) → скриншоты
вручную поднятого dev-сервера на тестовой БД для каждой затронутой
страницы, включая мобильный вьюпорт там, где менялась адаптивность →
`git status --short` для проверки точного набора файлов → коммит на
русском с обоснованием → push только в `origin/2.0`.
