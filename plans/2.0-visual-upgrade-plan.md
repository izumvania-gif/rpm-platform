# Визуальный апгрейд 2.0-представлений

## Контекст

Все 8 фаз `plans/platform-views-plan.md` сделаны — `/people`, `/pm` (роадмап-список,
Гант, команда, экшн-планы, процесс), `/cpo`, `/public`, `/marketing-hub`,
`/sales-hub` реальны и функциональны. Прямой запрос: «Create a plan for a visual
upgrade of all features that you made for 2.0. We need really good high level
frontend design, like it was made by pro devs.» Это ровно та же ситуация, что
привела к `plans/archive/visual-redesign-plan.md` в 1.0 — функциональность
готова раньше визуальной идентичности. Этот план — тот же проход, но для 2.0-хабов,
и **строит поверх уже существующих токенов 1.0**, не изобретает новую палитру
(в отличие от 1.0-редизайна, где токены создавались с нуля).

## Аудит текущего состояния

Скриншоты сняты с реального сид-продукта («Аудит Демо») через тестовую БД —
`/people`, `/pm` (список и Гант), `/cpo`, `/public`, `/marketing-hub`,
`/sales-hub`.

**Сквозная проблема на всех 6 страницах:** каждая секция — это `Card
variant="content"` с одинаковой рамкой `border-l-4 border-primary` + lucide-иконка

- заголовок (см. `DashboardWidgetCard` и одноимённый паттерн, руками повторённый
  в `app/pm/page.tsx`, `app/public/page.tsx`, `app/sales-hub/page.tsx`). Секции
  визуально неотличимы по важности: «Роадмап» и «Команда» на `/pm` выглядят
  одинаково весомыми, хотя первое смотрят каждый день, второе — справочно.
  Ничего из 2.0 не получило «геройской» обработки, которую в 1.0 получили узел
  JTBD-графа, композиция дашборда, kanban-карточки, оверлей клавиатурных
  сокращений.

**`/people`** — голый hairline-список: имя + текст роли + кнопка-булавка,
ничего больше. Ни аватара, ни инициалов, ни цветового кода — при том, что
`Person` теперь используется как визуальная сущность в 4 местах (список,
`/pm` → Команда, узлы графа процесса, «Ответственный» на пунктах роадмапа), и
нигде не имеет собственной визуальной идентичности.

**`/pm`** — 4 одинаковых блока подряд (Роадмап, Команда, Экшн-планы, Процесс),
без иерархии. Узлы `ProcessStepNode` (`components/process-graph/process-step-node.tsx`)
— белая карточка с текстом и мелкой иконкой `User`, без какой-либо визуальной
дифференциации по роли, в отличие от геройской обработки узла JTBD-графа.
Сам Гант (`components/roadmap-gantt/gantt-chart.tsx`) уже получил осознанную
dataviz-проработку в прошлой итерации (тоновые бары, легенда статусов, линия
вехи с подписью, месячная сетка) — ему требуется наименьшая доработка.
**Найдена и не связанная с визуалом проблема копирайта:** футер страницы
до сих пор показывает «Раздел в разработке — см. plans/platform-views-plan.md.»
— остаток эпохи `PersonaStub`, все секции которого теперь реальны и рабочие.

**`/cpo`** — тот же блочный паттерн. KPI-числа в «Ключевые направления
развития» — чёрный `font-mono text-2xl`, без какого-либо визуального сигнала
о критичности (0 выглядит так же тревожно, как и положительное число).
«Экосистема» показывает два списка пересечений рядом без визуальной связи
между ними и продуктами, которых они касаются.

**`/public`** — **самая серьёзная находка аудита.** Это единственный
по-настоящему открытый, безсессионный маршрут в приложении (см.
`app/public/page.tsx`'s комментарий и `CLAUDE.md`), но рендерится под тем же
глобальным `SiteNav` (`app/layout.tsx` монтирует `<SiteNav />` один раз для
всего приложения), что и внутренние страницы: полное меню Продукты/Сегменты/
Исследования/Маркетинг/JTBD с CRUD-подменю, поиск по всем внутренним данным,
`PersonaSwitcher`, подсказка клавиатурных сокращений. Внешний посетитель без
логина видит интерфейс внутреннего инструмента управления продуктом. Это не
только эстетическая, но и содержательная ошибка — открытая страница обязана
выглядеть как открытая страница.

**`/marketing-hub`** — цепочка «JTBD → Фича → RTB» размечена как вложенный
список с вертикальной чертой слева, хотя подзаголовок секции буквально
описывает её как цепочку через «→». Визуально это не читается как цепочка.

**`/sales-hub`** — очень разреженная страница, много пустого пространства.
Форма «Есть ли у нас фича X?» — ровно то, ради чего существует раздел (см.
подзаголовок страницы), но оформлена как рядовая инлайн-форма без какого-либо
визуального веса, соразмерного её роли главного инструмента хаба.

## Направление дизайна

**Токены не меняются.** Палитра (`--primary` окисленно-красный, тёплый
off-white фон, белые карточки, hairline `--border`, `--radius: 0.375rem`,
`--ease-signature`), шрифтовая тройка (Manrope/Inter/IBM Plex Mono),
4-тональная система `--signal-violet/red/blue/slate`, тёмная тема — всё это
уже зафиксировано 1.0-редизайном и используется этим планом как данность, не
как объект пересмотра.

**Что добавляется — 5 приёмов, переиспользующих существующие токены:**

1. **`PersonAvatar`** — детерминированный инициал + цвет, выбранный из уже
   существующих 4 `--signal-*` тонов по хэшу имени (не новая палитра — те же
   4 тона, что уже красят Badge/SignalBadge). Даёт `Person` визуальную
   идентичность один раз, переиспользуется в `/people`, `/pm` → Команда, узлах
   графа процесса и подписях «Ответственный» на пунктах роадмапа.
2. **Иерархия секций** вместо повторения одного и того же блока: на страницах
   с несколькими секциями одна — «первичная» (полный вес: `border-l-4`,
   крупный заголовок), остальные — «вторичные» (более лёгкая рамка, меньший
   заголовок, без полноразмерной шапки). Явное решение о том, что первично на
   каждой странице — ниже, в разделе по страницам.
3. **Тон на KPI-числах** (`/cpo`): число красится в `signal-red` при
   count > 0 на «плохих» метриках (пробелы, зависшие гипотезы) и остаётся
   нейтральным text-foreground при 0 — тот же принцип, что уже применяется в
   Badge/RoadmapStatus, просто впервые применённый к голым числам.
4. **Видимый коннектор для цепочек** (`/marketing-hub`): JTBD → Фича → RTB
   рисуется как реальная вертикальная цепочка с точками-маркерами на каждом
   уровне и соединительной линией — не новый компонент библиотеки, чистый
   CSS, тот же приём, что уже применён к линиям вех в Ганте.
5. **`PublicHeader`** — единственный настоящий «сигнатурный» элемент этого
   прохода (frontend-design: «spend your boldness in one place»). `/public`
   получает свою, отдельную от `SiteNav`, минимальную шапку: вордмарк + подпись
   «Открытый дашборд компании» + переключатель темы — без поиска, без
   CRUD-навигации, без `PersonaSwitcher`, без подсказки горячих клавиш.
   Технически: `SiteNav` уже клиентский компонент с `usePathname()` — добавляем
   в него ветвление по префиксу `/public`, рендерящее `PublicHeader` вместо
   основной разметки, без реструктуризации `app/layout.tsx`.

Всё остальное — точечная доводка внутри уже существующих карточек
(`DashboardWidgetCard`, `Card variant="content"`), без новых зависимостей.
Крупная форма поиска на `/sales-hub` получает больше визуального веса (шире,
с явной рамкой и увеличенным полем ввода), но остаётся тем же HTML-`<form>`.

## Пофайловые геройские решения

- **`/people`** — список остаётся hairline-списком (это установленный 1.0-хвостом
  паттерн для длинных списков, см. `CLAUDE.md`: карточные сетки на `/segments`,
  `/competitors` и др. были осознанно заменены на плотные списки, не наоборот)
  — `PersonAvatar` добавляется в начало каждой строки вместо того, чтобы менять
  сам паттерн списка.
- **`/pm`** — «Роадмап» остаётся первичной секцией (единственная с кнопкой
  действия в шапке того же веса и переключателем Список/Гант — уже так).
  «Команда», «Экшн-планы», «Процесс» получают вторичное, более лёгкое
  оформление шапки (без `border-l-4`, меньше отступов). Узлы
  `ProcessStepNode` получают `PersonAvatar` вместо иконки `User`. Футер:
  строка «Раздел в разработке…» удаляется — все секции реальны.
- **`/cpo`** — 4 KPI-плитки в «Ключевые направления развития» красятся по
  `signal-red`/нейтральному правилу выше. «Экосистема» остаётся как есть по
  структуре (двухколоночная), но карточки пересечений получают счётчик
  продуктов как небольшой Badge вместо голого текста через запятую.
- **`/public`** — новый `PublicHeader`. Карточки секций (2 штуки: Продукты,
  Публичный роадмап) получают вторичное оформление, раз здесь всего 2 секции
  и полноразмерная шапка избыточна.
- **`/marketing-hub`** — цепочка JTBD→Фича→RTB — коннектор из раздела выше.
  «Скоро» без изменений (уже читается нормально).
- **`/sales-hub`** — форма «Есть ли у нас фича X?» увеличивается: более
  крупный заголовок секции, поле ввода на всю ширину с явной рамкой,
  результаты остаются как есть (уже используют `signal-*` тона по типу
  ответа — это уже хорошо).

## Осознанно вне рамок

- Никакой новой цветовой палитры или шрифтов — только уже зафиксированные
  токены 1.0.
- Никакой реструктуризации `app/layout.tsx` — `PublicHeader` реализуется
  условным рендерингом внутри уже существующего клиентского `SiteNav`.
- `Person`-инлайн-создание по-прежнему не добавляется (см. `CLAUDE.md`) —
  этот план про визуал, не про новые формы взаимодействия.
- Гант-диаграмма (`components/roadmap-gantt/gantt-chart.tsx`) не
  переписывается — она уже прошла отдельный dataviz-проход в прошлой
  итерации; возможна только точечная доводка отступов, если понадобится при
  визуальном QA.
- Реальная защита `/public` (RBAC/аутентификация) не в рамках — план решает
  только визуальную/содержательную проблему «выглядит как внутренний
  инструмент», не техническую границу доступа (которая по-прежнему в
  бэклоге, см. `plans/platform-views-plan.md` §2/§9 «Явно вне рамок»).

## Ритуал проверки

Идентичен использовавшемуся во всех предыдущих фазах 2.0: `npm run lint &&
npm run typecheck` → `npm run test:unit` → `npm run test:integration` (реальный
Postgres, `rpm_platform_test`) → `npm run test:e2e` (headless Chromium,
`PLAYWRIGHT_CHROMIUM_PATH` обязателен в этом окружении) → скриншоты вручную
поднятого dev-сервера на тестовой БД для каждой затронутой страницы (светлая
и тёмная тема, где это осмысленно) → `git status --short` для проверки
точного набора файлов → коммит на русском с обоснованием → push только в
`origin/2.0`.
