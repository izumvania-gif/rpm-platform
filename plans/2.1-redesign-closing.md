# Закрытие редизайна 2.1: что изменилось

Редизайн 2.1 закончен — все 12 фаз и сквозное. `plans/2.1-redesign-plan.md`
записывает решения по мере их принятия: 836 строк, шесть правок к хендоффу и
по разделу «что вышло на деле» на каждую фазу. Этот документ — другой жанр:
**результат в одном месте**, для тех, кто не будет читать план целиком.

Разбивка здесь **не по фазам, а по смыслу**. Фаза — это единица работы, и
порядок у неё технический (сначала то, что даёт ценность независимо и не
ломает тесты). Читателю нужно другое: что в продукте стало иначе. Одно
изменение иногда собрано из двух фаз, а одна фаза иногда попала в два раздела.

Тезисы для рассказа наружу — отдельный документ:
[`docs/presentation/theses.md`](../docs/presentation/theses.md).

(фаза 2), и они добавлены ровно потому, что без них одно из изменений было бы
враньём: без `Hypothesis.validationCriterion` статус «Подтверждена» остаётся
мнением, а без `Insight.stance` полосу баланса не из чего собрать.

Рост числа тестов (+172 unit, +41 интеграционных, +34 E2E) непропорционален
объёму кода не случайно: редизайн вводил **правила**, а правило, не
закреплённое тестом, — это комментарий.

## Одиннадцать изменений

### 1. Гипотеза перестала быть мнением

**Было.** Гипотеза имела статус (Черновик → На проверке → Подтверждена /
Опровергнута) и число приоритета. Что означает «Подтверждена», не было
записано нигде: это было утверждение автора о самом себе. Инсайты в базе были,
но привязать инсайт к гипотезе схема не позволяла — доказательства и вывод
жили в разных концах приложения.

**Стало.** Три вещи, работающие вместе:

- **Критерий проверки** (`Hypothesis.validationCriterion`) — «при каком
  результате считаем подтверждённой», написанный **до** проверки. Поле
  необязательное: заставить придумать критерий на месте — это получать
  отписки, а пустое поле честно означает «критерия нет» и так и попадает в
  чек-лист.
- **Доказательства со стороной** (`Insight.hypothesisId` + `Insight.stance` =
  за / против / без стороны) и полоса баланса. Сторона не выводится из текста:
  определить «за» или «против» по формулировке — значит проголосовать за
  пользователя. Нейтральная сторона существует специально — наблюдение имеет
  право не занимать позицию, а принуждение к выбору положило бы в полосу
  выдуманные голоса.
- **Чек-лист готовности** из четырёх условий (`lib/hypothesis-readiness.ts`,
  чистый, 14 юнит-тестов) с кнопкой действия на каждой невыполненной строке.

**Инвариант, который делает это чем-то большим, чем виджет.** Условия
считаются **по фактам, а не по счётчикам**: «минимум 3 доказательства» — это
`insights.length >= 3` по привязанным инсайтам, а не число разговоров у
продукта. Ноль доказательств поэтому не может дать полный балл — иначе экран
одновременно сказал бы «готова к решению» и «решать нечего».

Два уточнения, которых в плане не было и которые пришлось вывести из практики:
у **опровергнутой** гипотезы фичу не спрашивают (проверенное «нет» — законный
результат исследования, а не недоделка), поэтому знаменатель падает до 3; а
доли в полосе считаются **от высказавшихся**, при этом безучастные инсайты
считаются и называются отдельно, а не растворяются в одной из долей.

**Дальше это уехало на главную** (фаза 10): очередь «Требуют решения» считает
готовность по всей базе **тем же кодом**, а не второй копией правил — две
реализации «готова к решению» разошлись бы на первой правке, и дашборд начал
бы звать решать то, что карточка считает недоделанным.

**Чем закреплено:** 14 юнит-тестов на готовность (в т. ч. «ноль доказательств
никогда не даёт полный балл»), юнит-тесты на очередь, E2E
`hypothesis-evidence.spec.ts`.

> Это то изменение, ради которого редизайн затевался. После фазы 3 главная
> претензия заказчика была закрыта, даже если бы всё остальное остановилось.

### 2. Цвет получил одно правило

**Было.** `--primary` — тёмно-красный `#b52318`, и этим же красным красились
разрывы: пустые ячейки в матрице связей, тревожные числа на карточках модулей,
строки отчёта «Пробелы». То есть на экранах, **весь смысл которых — показывать
разрывы**, «нажми здесь» и «здесь проблема» были одного цвета.

**Стало.** Правило в одну строку: **красный — действие и активное состояние,
янтарный — разрыв и то, что требует внимания, зелёный — подтверждённое.**
`--primary` переведён на фирменный `#dd2233` из брендбука (Pantone 1795 C).

Шаги янтарного и зелёного **посчитаны скриптом**, а не подобраны глазом —
контраст к обеим поверхностям (страница и карточка) в обеих темах. Два
следствия, которые нельзя «починить обратно»:

- **Янтарный физически не берёт 3:1 к почти белому фону** ни на какой
  светлоте, на которой он ещё читается как янтарный. Поэтому `-border` уведён
  в охристый `33 90% 38%` (3,98:1) — этот шаг используется для иконок, которым
  контраст обязателен.
- **Янтарный блок красится рамкой и заголовком, но никогда не заливкой.**
  Подписи внутри идут `text-muted-foreground`, а этот токен считался под
  `--background`; залить фон значило бы поставить текст на поверхность, под
  которую его контраст никто не считал.

**Одно отступление, названное вслух.** `REJECTED` у гипотезы остался красным:
это терминальный статус, всегда подписанный словом «Опровергнута», а не
индикатор проблемы и не кнопка. Отступление описано в `lib/labels.ts` рядом с
кодом, а не только в плане.

**Побочно найдено и починено.** (а) Давний недобор контраста в тёмной теме:
белый текст на прежнем `--primary` давал 4,20:1, то есть AA не проходил;
теперь 4,65:1. (б) `SignalTone` работал сразу на два несовместимых смысла —
принадлежность к типу (тип JTBD-задачи, аватар человека) и состояние; после
добавления янтарного и зелёного аватар по хешу имени рано или поздно получил
бы цвет «здесь разрыв». Набор разведён на `signalTones` и `categoricalTones`.

### 3. Продукт стал контекстом, а не фильтром в голове

**Было.** Активный продукт хранился в `localStorage`, то есть был известен
только клиенту. Страницы со списками — Server Components, которые ходят в
Prisma **на сервере**, и `localStorage` оттуда не читается. Поэтому девять
списков показывали записи всех продуктов сразу, а «какой продукт я сейчас
веду» существовало только в голове пользователя.

**Стало.** Активный продукт живёт в **cookie** — единственном транспорте,
который видит сервер.

Замер, который выбрал решение: **77 из 78 страниц уже `force-dynamic`**, то
есть рендерятся на каждый запрос — `cookies()` не отнимает ни одной
оптимизации кэша, потому что отнимать нечего. Альтернатива `?productId=` в URL
потребовала бы протащить параметр через **162 `<Link>`** и противоречила бы
решению держать маршруты плоскими.

Три правила, которые нельзя ослаблять:

- **Cookie проверяется на владение.** Значение приходит от клиента, его можно
  поставить руками; без проверки чужой или уже удалённый id молча стал бы
  «активным продуктом» и отфильтровал бы все списки в пустоту без единого
  объяснения.
- **Пустой контекст даёт `{}`, а не `{ productId: null }`.** Второе — это
  условие «у записи нет продукта», другое и ложное утверждение.
- **Пишет cookie Server Action, а не клиент.** Серверу надо перерисовать
  списки; запись с клиента после редиректа он бы не увидел, и первый же список
  показал бы старый контекст.

**Расхождение с планом, принятое осознанно.** План требовал выбрасывать на
Обзор карточку записи из неактивного продукта. Не сделано: ссылка на запись —
самый частый способ показать коллеге, о чём речь, и редирект её ломает; при
этом запись своя, границы доступа тут нет — есть рассинхрон контекста.
Наказывать человека за состояние, которого он не выбирал, неправильно. Но и
показать молча нельзя — тогда запись видна на карточке и отсутствует в списке
без объяснений. Поэтому третий вариант: показать, назвать причину янтарной
плашкой и дать кнопку, переключающую продукт одним действием.

**Ещё одно расхождение, в меньшую сторону.** План говорил «39 страниц с
продуктовыми запросами получают фильтр». Отфильтровано **девять** — именно они
смешивали продукты. У отчётов, `/pm` и `/sales-hub` были свои переключатели, и
они с фазы 4 пишут ту же cookie, то есть контекст стал общим без единой правки
в них.

### 4. Меню перестало быть списком разделов

**Было.** Три конкурирующие навигации: верхнее меню, плитка модулей на
дашборде и подменю разделов. Верхний ряд уже физически не помещался — его
`nav` с нерастягивающимися ссылками отдавал лишнюю ширину **поверх** соседей,
и на 1024px «Инбокс» и поле поиска переставали нажиматься.

**Стало.** Меню читается как метод, а не как оглавление:

```
Обзор │ Сегменты › JTBD › Гипотезы › Фичи › Обещания │ Доставка · База знаний · Команда
```

Шевроны между пятью звеньями — **утверждение о порядке**: цепочка дискавери
действительно последовательна, и именно её считают `/reports/gaps` и лента
цепочки на карточках. Группы после неё разделены точками, потому что цепочку
не продолжают: доставка — это исполнение, база знаний — сырьё, команда — люди.

Два ряда — **арифметика, а не вкус**: девять пунктов первого уровня против
прежних пяти рядом с логотипом, поиском и четырьмя кнопками не помещаются.
Ряд 1 отвечает на «кто я и где я работаю», ряд 2 — на «куда я иду». После
правки замерено: на 1024, 1280 и 1440 все контролы шапки кликабельны — в том
числе на 1024, где наезд существовал ещё до редизайна.

**Плитка модулей удалена** вместе с девятью `count()`-запросами, которые
дашборд делал только ради неё. Переключатель режима раскрытия переехал в ряд 2
и показывается теперь всегда: раньше он прятался при полном режиме, потому что
«место в шапке дефицитно» — со второй строкой это перестало быть правдой.

**«Маркетинг» стал «Обещаниями».** Слово «маркетинг» называет отдел, а не
содержание. Маршрут остался `/marketing` и модель осталась `RTB`:
переименование ярлыка — не повод ломать адреса.

**Сверка маршрутов сделана тестом, а не глазами.**
`tests/unit/nav-chain.test.ts` обходит `app/**/page.tsx` и требует пункт меню
для каждого раздела верхнего уровня, а также запрещает пункт, ведущий в
несуществующий маршрут; исключения перечислены явно и с причиной. Оправдался
сразу: первый же прогон поймал `/jtbd/graph`, который был подпунктом старого
меню и потерялся бы молча. Ручная сверка «по списку из 78 страниц» такое
пропускает и, главное, не повторяется на каждом прогоне.

### 5. Разрыв в цепочке стал кнопкой

**Было.** Лента цепочки на карточке JTBD, гипотезы и фичи рисовала недостающее
звено пунктиром со ссылкой «+ добавить» — то есть уводила с карточки, на
которой разрыв виден, на форму создания.

**Стало.** Пустой слот — это пикер: выбрать существующую запись или создать
новую прямо там, без перезагрузки и без ухода со страницы.

**Главное решение фазы — кнопку получил не каждый слот.** Из одиннадцати
пустых слотов на трёх карточках одним действием чинятся восемь;
`lib/chain-gap.ts` перечисляет их поимённо, а юнит-тест требует именно этот
список, чтобы девятый нельзя было добавить молча. Оставшиеся три —
«Маркетинг» на карточке JTBD и гипотезы, «Сегмент» на карточке фичи — разрывы
**через два звена**. Пикер там означал бы «привяжем к какой-нибудь фиче на
выбор системы», то есть придумал бы за пользователя связь, которой он не
делал. **Кнопка обещает, что после клика разрыва не будет; там, где обещание
невыполнимо, осталась прежняя ссылка.**

Связь ставится и оптимистично, и по-настоящему: клиент показывает результат
сразу, `router.refresh()` перерисовывает ленту на сервере (она собирается
там). E2E проверяет отсутствие перезагрузки не косвенно — перед кликом в
`window` кладётся метка, после проверяется, что она пережила; без этого тест
прошёл бы и на старом поведении «слот ведёт на форму».

**Пикер гипотезы не предлагает чужое.** `Hypothesis.jtbdId` одна на запись, и
«связать» с уже привязанной гипотезой означало бы «отобрать». Кандидаты —
только гипотезы без задачи, и то же условие продублировано на записи
(`updateMany ... where jtbdId: null`): между показом списка и кликом связь мог
поставить кто-то другой.

Оба id проходят `denyUnowned` — как и в `setLink`: проверять только якорь
значило бы оставить `connect` межтенантной записью.

### 6. Пять карточек стали одним шаблоном

**Было.** `/segments/[id]`, `/jtbd/[id]`, `/features/[id]`, `/marketing/[id]` и
`/competitors/[id]` — пять страниц об одном и том же по структуре, с разной
вёрсткой, разным порядком кнопок и разным голосом пустых состояний.

**Стало.** Один шелл `components/shared/record-page.tsx`: крошки
(Продукт / Раздел), одинаковая шапка с пятью кнопками в одном порядке, слот
ленты цепочки, ряд мета-чипов, `<dl>` ключевых полей и `RecordSection` для
связанных записей — с одним стилем счётчика и одним голосом пустых состояний.
Плюс блок **«Что мешает»** (`lib/record-blockers.ts`, чистый).

**Шаблон принимает узлы, а не строки, и только поэтому инлайн-правка выжила.**
Все пять страниц правят поля на месте через `InlineEditableField`; шаблон с
`title: string` нарисовал бы заголовок сам — и убил бы ровно то, о чём план
предупреждал (Server Component может передать в Client Component только
сериализуемые данные или забинденный `'use server'`-экшен).

**«Что мешает» намеренно не пересказывает ленту цепочки.** У JTBD и фичи лента
уже показывает разрывы и с фазы 7 чинит их в слоте; продублировать их в блоке
значило бы повторить ошибку фазы 3, где чек-лист и «Что можно сделать»
оказались пересказом друг друга. Поэтому у JTBD здесь одно условие —
подтверждение исследованием, у фичи одно — связь с гипотезой (её на ленте фичи
нет вовсе), а полный набор у сегмента, обещания и конкурента, у которых ленты
нет. Юнит-тест проверяет и обратное: что у JTBD не появилось ключей
`no-segment` / `no-hypothesis` / `no-feature`.

**Условие без кнопки — жалоба, а не задача**, поэтому действие обязательно у
каждого, и тест проверяет это на всех «худших» входах разом. Куда ведёт
кнопка, решает правило фазы 3: **чинится здесь — якорь к секции, требует
другой страницы — ссылка туда**. У неподтверждённого JTBD кнопка ведёт к
привязке исследования, а не к галочке: подтверждение означает «есть
исследование», и ставить его одним кликом значило бы обманывать самого себя.

### 7. «Доставка» стала разделом, а не длинной страницей

**Было.** `/pm` — одна длинная страница: роадмап, Гант (переключателем внутри
карточки), процессы, экшн-планы, команда. Добавление записи внизу уводило
скролл — известная проблема, ради которой существовал отдельный компонент
`ScrollToSection` и query-параметр `scrollTo`.

**Стало.** Пять настоящих маршрутов: Роадмап · Гант · Процессы · Экшн-планы ·
Команда, `/pm` редиректит на `/pm/roadmap` (перенося `?productId=`).

**Вкладок пять, а не четыре из плана:** «Команда» на `/pm` есть, работает и не
принадлежит ни роадмапу, ни процессу — спрятать её под одну из четырёх было бы
произволом.

**Настоящие маршруты, а не `?tab=`:** у пункта меню обязан быть адрес
(`nav-chain.test.ts` этого требует), и вкладка, на которую нельзя дать ссылку,
— не вкладка. По той же причине убран прежний переключатель «Список / Гант»
внутри карточки: с «Гантом» отдельной вкладкой это был бы второй способ
переключить один вид на одном экране. `/cpo` свой похожий переключатель
сохранил осознанно — это одна обзорная страница, а не раздел с подуровнем.

`ScrollToSection` и `scrollTo` **удалены**: возвращать скролл больше не к
чему, каждый раздел — свой экран. Это и есть причина, по которой план назвал
фазу дешёвой.

`lib/pm-nav.ts` — **один источник** и для полосы вкладок на странице, и для
второго уровня «Доставки» в меню. Два списка разошлись бы на первой правке.

### 8. Главная получила несъёмный каркас

**Было.** Всё на дашборде было виджетами настраиваемой сетки — включая цепочку
дискавери и сводку пробелов. То есть вопросы «где мы» и «что решать» можно
было спрятать, хотя их задаёт каждый, кто открывает главную. Вывод про слабое
звено стоял сноской под пятью полосками, то есть читался последним, хотя он и
есть главное, что говорит экран.

**Стало.** Цепочка и пробелы — каркас страницы, а не виджеты (из реестра оба
ушли, иначе рисовались бы дважды). Сохранённые в браузерах раскладки
переживают это **без миграции**: `reconcileDashboardLayout` выбрасывает
неизвестные id — ровно тот механизм, ради которого он был написан.

Плашка слабого звена переехала наверх, стала янтарной и получила кнопку в
очередь пробелов; из карточки цепочки тот же вывод убран, чтобы не стоять на
экране дважды.

**Действительно новое здесь — очередь «Требуют решения».** Фаза 3 научила
карточку считать готовность, но ответ был виден только внутри карточки.
Очередь считает то же самое по всей базе тем же кодом. В неё попадает **только
то, что можно решить прямо сейчас**: «почти готово» не добавляется, иначе
обещание очереди перестало бы быть правдой. Пустая очередь пишет «решать пока
нечего», а не «нет данных» — это осмысленный ответ. Сортировка по числу
доказательств; ранжировать «по единодушию» читалось бы удобнее, но это уже
суждение о том, какое решение проще, а не факт о данных.

### 9. База знаний стала одним разделом

**Было.** `/research`, `/conversations` и `/insights` — три несвязанные
страницы, хотя это три стадии одного: исследование как активность, разговор
внутри него, инсайт из разговора.

**Стало.** Общая полоса вкладок (`lib/knowledge-nav.ts` — тот же источник, что
и для подменю в меню) и **бейдж связи** в каждой строке списка.

**Маршруты остались прежними.** Общий префикс `/knowledge` сломал бы сотню
существующих ссылок ради адресной строки; вкладки говорят, что страницы
связаны, а не где они лежат.

Бейдж считает существующие факты и ничего не изобретает — то же правило, что у
«Что мешает». Янтарный только у разрыва: связь, которая есть, — норма, а не
новость. Различие, которое пришлось выдержать: у исследования бейдж
показывает **число** (разбивка в подсказке), у инсайта — **имена** связей. У
инсайта каждая связь одна, и «3 связи» сказало бы меньше, чем «Сегмент · JTBD
· Гипотеза»; у исследования наоборот — на него ссылаются десятки записей.

### 10. Графы остались двумя — и это решение, а не пропуск

**Было и осталось.** `/jtbd/graph` (как задачи связаны между собой) и
`/products/[id]/canvas` (сходится ли цепочка). План требовал слить их в один
граф с фильтром по типу узла.

**Слияния не было.** Взявшись за фазу, я обнаружил, что против неё **уже
написан аргумент** — в шапке `lib/product-canvas.ts`, с момента постройки
холста в 2.0. Разбор его подтвердил: общего у двух графов только React Flow.
Разные вопросы, разные модели узлов (один тип против трёх), разные жесты
(перетащить-в-родителя и ребро последовательности против направленной связи по
цепочке и создания двойным кликом), разные таблицы раскладок (`JtbdGraphLayout`
по представлению на сегмент против `ProductCanvasLayout`). Один холст с
фильтром отвечал бы на оба вопроса хуже, чем два отвечают каждый на свой, —
и это была бы переписка двух работающих фич с E2E-покрытием ради стройности.

Заказчику предъявлены три варианта (полное слияние / фильтр и раскладка без
слияния / пропустить фазу); **выбран средний**. Взято ровно то, ради чего фаза
затевалась:

- **фильтр по типу узла** на холсте — три переключателя со счётчиком каждого
  типа. Важное: признак «цепочка оборвана» считается на **полных** данных на
  сервере, поэтому задача без гипотезы остаётся пунктирной и тогда, когда
  гипотезы скрыты. Иначе фильтр показывал бы благополучие, которого нет;
- **слоистая раскладка** (`layoutCanvas`) вместо прежней «колонка на тип, по
  порядку появления», где сегмент мог оказаться в одном конце холста, а его
  задачи в другом. Она же за кнопкой «Разложить заново»;
- **взаимные ссылки** между двумя графами (с холста на граф ссылка была,
  обратной не было).

**Ручная расстановка сохранена** (правка 5 плана): вычисленная раскладка —
только начальное положение, сохранённая позиция всегда побеждает. Задача,
принадлежащая нескольким сегментам, ставится первым сегментом, который её
называет — выбор произвольный, но детерминированный, иначе раскладка «прыгала»
бы между перезагрузками. Юнит-тест проверяет именно это.

### 11. Сквозное: три подозрения плана, все три подтвердились

- **Плюрализаций было две, и они уже разошлись.** `lib/delete-impact.ts`
  возвращал форму слова и брал `Math.abs`; `lib/utils.ts` возвращал «число +
  форму» и абсолютного значения не брал — на отрицательном счётчике выдал бы
  «−1 продуктов». Счётчики в приложении неотрицательны, поэтому ошибка не
  проявлялась, но выбор реализации по имени файла — это уже расхождение.
  Теперь `lib/plural.ts`: одна реализация, две обёртки (оба вида вызова
  настоящие — где-то нужна только форма, где-то готовая строка).
- **Автоматический нижний регистр нашёлся в четырёх местах, и в трёх ломал
  акронимы:** «Слабое звено — jtbd» (мой же баг из фазы 10), «jtbd: 3» и
  «rtb: 1» в инбоксе, «Привязан: сегмент, jtbd» в бейдже инсайта. У плашки
  заодно поменялось тире на двоеточие — оно позволяет оставить слову регистр,
  не ломая фразу.
- **Нулевая длительность нашлась одна:** подсказка полосы Ганта у однодневного
  пункта писала «1 янв 2026 – 1 янв 2026». `barDateRange` сравнивает уже
  **отформатированные строки**, а не миллисекунды: если обе даты подписаны
  одним днём, диапазон между ними бессмыслен независимо от того, сколько между
  ними часов.

## Что редизайн оставил в коде помимо экранов

Экраны можно перерисовать. Правила пережить редизайн сложнее, поэтому они
записаны рядом с кодом, а не только в плане, и почти каждое закрыто тестом.

| Правило                                                                   | Где живёт                                                      |
| ------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Красный — действие, янтарный — разрыв, зелёный — подтверждённое           | `app/globals.css`, `lib/labels.ts`                             |
| Янтарный блок — рамка и заголовок, никогда не заливка                     | `record-blockers.tsx`, `dashboard-weak-link.tsx`               |
| Идентичность красится `categoricalTones`, состояние — `signalTones`       | `lib/signal-colors.ts`, `person-avatar.tsx`                    |
| Условие считается по факту, а не по счётчику                              | `lib/hypothesis-readiness.ts`                                  |
| Условие без кнопки — жалоба, а не задача                                  | `lib/record-blockers.ts` (+ тест на «худший вход»)             |
| Чинится здесь — якорь к секции; нужна другая страница — ссылка туда       | фазы 3, 8; тест на strict-mode неоднозначность                 |
| Кнопка «связать» стоит только там, где после клика разрыва точно не будет | `lib/chain-gap.ts` (+ тест на точный список из 8)              |
| Один факт — одно хранилище                                                | `lib/product-context.ts` (cookie, миграция из LS)              |
| Один список — один источник                                               | `PM_TABS`, `KNOWLEDGE_TABS`, `hypothesisReadiness`, `pluralRu` |
| Шаблон принимает узлы, а не строки                                        | `components/shared/record-page.tsx`                            |
| Ничего не выдумывать за пользователя                                      | сторона инсайта, категория JTBD, `lib/key-phrase.ts`           |
| Каждый раздел имеет пункт меню, каждый пункт — существующий маршрут       | `tests/unit/nav-chain.test.ts`                                 |

Последняя строка — единственный тест в проекте, который проверяет **структуру
приложения**, а не поведение кода, и он окупился на первом же прогоне.

## Чем всё это проверено

Перед каждым пушем — полная пирамида, не выборочно:

```
npm run lint          ✓
npm run typecheck     ✓
next build            ✓
321 unit              ✓
295 integration       ✓
122 E2E               ✓ (0 упавших, 0 нестабильных, 19,9 мин)
```

E2E гоняются против `next dev` по общей тестовой базе без сброса между
спеками, поэтому каждый спек называет записи через `uniqueName()`. CI на
GitHub Actions повторяет всё это плюс production-сборку на каждый push и PR.

Отдельно стоит сказать, чего эта зелёная колонка **не** доказывает:
приложение по-прежнему однопользовательское (`DEFAULT_USER_ID`), нигде не
развёрнуто и не проверялось на реальной многопользовательской нагрузке. Гарды
владения (`lib/ownership.ts`, 21 модель) написаны и покрыты тестом изоляции
именно для того, чтобы включение настоящих сессий не превратило 64 мутации в
IDOR-уязвимости одной строкой, — но сессии не включены.
