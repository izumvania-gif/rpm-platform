# План внедрения AI

Статус: черновой анализ, ничего из этого не реализовано. Цель документа —
разложить «где вообще в RPM Platform уместен AI» на конкретные точки
интеграции, привязанные к существующим моделям/экшенам/страницам, и
предложить архитектуру подключения. Реализация начнётся отдельными фазами
после того, как объём и порядок фаз согласован — по аналогии с
`plans/archive/dashboard-redesign-plan.md` и `plans/archive/visual-redesign-plan.md`.

Приоритизация точек интеграции в §2 и §4 опирается на
`plans/pm-time-allocation-research.md` — отдельное кабинетное исследование
о том, на что PM реально тратят время по опубликованным опросам индустрии;
там же — ранжированный список кандидатов на автоматизацию с обоснованием.

## 0. Что изменилось по сравнению с исходным ECHO-спеком

Оригинальный спек (`plans/archive/ECHO_functional_requirements.md` §10, §14)
предполагал отдельный AI-сервис (Python/FastAPI) с LLM + RAG по базе знаний
продукта, поддержку нескольких распределённых агентов и трекинг через
LangFuse — то есть по сути отдельный бэкенд. `plans/backlog.md` фиксировал
это как «архитектурно не начато».

Сейчас условия проще и конкретнее: **AI подключается через локальный
корпоративный API — URL + access token**, то есть это просто ещё один HTTP-
эндпоинт, вызываемый напрямую из Next.js Server Actions/Route Handlers, без
отдельного сервиса, без очереди задач, без RAG-инфраструктуры на старте.
Это меняет архитектуру разительно: не «новый сервис», а «новый тонкий
клиент внутри монолита» (см. §3). Многоагентность, LangFuse, RAG по базе
знаний — остаются возможными более поздними шагами, но не обязательным
стартовым условием.

## 1. Принцип отбора точек интеграции

Для каждой точки ниже оценены:

- **Вход** — что реально уже есть в БД/на экране для промпта (без нового
  сбора данных с нуля — это важно, у продукта уже 11 моделей контента).
  Раздутого набора наименований («и это тоже удобно было бы») старались
  избегать: агент упомянут в контексте только когда для него есть a) вход и
  b) конкретный экшен/страница.
- **Выход** — куда конкретно пишется результат: значение поля,
  черновик записи, ранжированный список.
  «AI-функция» без конкретной точки записи не считается интеграцией —
  это либо чат (см. §2.7, отдельно и осторожно), либо не в этом плане.
- **Действие пользователя.** AI здесь нигде не пишет в базу напрямую и не
  подменяет решение продакт-менеджера — everywhere текущий паттерн:
  AI формирует черновик/предложение → показывается на экране (обычно как
  предзаполненная форма или отдельный список кандидатов) → человек
  подтверждает/правит → обычный Server Action создаёт/обновляет запись.
  Это соответствует уже принятому в проекте разделению «создать» vs
  «предложить, дать проверить» (ревью гипотез, инсайты — всё это ручной
  человеческий шаг).

## 2. Каталог точек интеграции

### 2.1 Онбординг нового продукта (наивысший приоритет)

Существующий мастер `/products/[id]/onboarding/{segments,jtbd,research,
hypotheses,competitors,features}` (`components/onboarding/wizard-shell.tsx`,
`wizard-steps.ts`) уже проводит пользователя по ровно тем шагам, где AI даёт
больше всего пользы за один проход — превратить пустой продукт в черновой
скелет за минуты вместо часов ручного ввода.

- **Профиль продукта → сегменты.** Вход: `Product.name` + `Product.description`
  (и любые `ProductResource` с URL — sales-kit, dev-docs, если уже добавлены
  на шаге создания продукта). AI предлагает 2–4 черновых сегмента (name,
  description, ориентировочный `audienceShare`) — рендерятся как список
  чекбоксов «добавить / не добавить» перед формой ручного создания на
  `/products/[id]/onboarding/segments`, а не создаются напрямую.
- **Профиль продукта (+ сегменты) → JTBD.** Это прямое попадание в
  формулировку из исходного запроса пользователя («автоматически создавать
  JTBD из профилей продукта»). Вход: `Product.description` + принятые на
  предыдущем шаге сегменты. Выход: черновые `JTBD` (title, category,
  description, jobType — BIG/CORE/SMALL/MICRO, разметка по методологии уже
  описана в `lib/jtbd-job-types.ts`/схеме) с привязкой к сегменту(ам),
  `confirmed: false` — они и так по умолчанию неподтверждённые, что здесь
  особенно уместно: сгенерированный черновик JTBD обязан пройти тот же путь
  подтверждения исследованием, что и вручную введённый (§2.9 в
  growth-plan.md, gaps-дашборд уже считает «JTBD без подтверждения» как
  индикатор). AI не обходит эту проверку — он просто наполняет её входом.
- **JTBD → гипотезы.** Вход: принятые JTBD + сегмент. Выход: черновые
  `Hypothesis.statement` в формате "Если..., то...", `status: DRAFT` —
  ровно тот статус, с которого гипотеза и так стартует вручную.
- **Профиль продукта → конкуренты (первичный список).** Вход:
  `Product.description`/индустрия. Выход: черновые `Competitor` (name, url,
  positioning) для проверки на шаге `.../onboarding/competitors` —
  человек мог не вспомнить всех игроков рынка сходу.
- **Профиль продукта → фичи/RTB.** Ниже приоритетом (фичи обычно точно
  известны продакту), но симметрично с остальными шагами — можно предложить
  типовые RTB-формулировки по описанию продукта на шаге features.

Технически — единственная новая non-redirecting точка на шаг: расширить
`createXQuick`-паттерн вариантом `suggestXFromProduct(productId)`,
возвращающим `{ ok: true, data: Draft[] } | { ok: false, error }` — тот же
контракт, что уже есть у quick-actions, только источник данных не форма, а
AI-ответ.

### 2.2 Сбор новостей по конкурентам

Второй explicit-запрос пользователя. `CompetitorNewsItem` (title, url, date,
note) сейчас — чисто ручной лог на странице `/competitors/[id]` (см. §2.9.4
growth-plan.md). Возможные уровни:

- **Уровень 1 (безопасный, реалистичный на первой итерации):**
  AI суммирует уже вставленный пользователем текст/URL в аккуратные title +
  note перед сохранением — то есть ассистирует вводу, а не ищет новости сам.
  Не требует выхода в интернет с бэкенда, не требует доверия к
  свежести/точности AI-поиска.
  - **Уровень 2 (полноценный «сбор»):** если у корпоративного API есть web-
    search/browsing-инструмент (это отдельный вопрос к владельцу API, не
    предполагать по умолчанию) — периодическая (по кнопке «Проверить
    новости» на `/competitors/[id]`, не по крону на старте) выборка новостей
    по `Competitor.name`/`url`, показанная как список кандидатов с источником
    и датой, которые пользователь по одному добавляет в лог. `lastCheckedAt`
    уже есть в схеме и явно предназначено для этого.
- Уровень 2 зависит от возможностей самого корпоративного API (см. §5,
  открытый вопрос) — не проектировать глубже до ответа на этот вопрос.

### 2.3 CustDev-разговоры → инсайты/JTBD/гипотезы

`Conversation.transcript` — это готовый неструктурированный текст, самый
богатый источник данных в системе, который сегодня никак автоматически не
обрабатывается. Прямое попадание в исходный ECHO-спек (§10.2: «AI-обработка
транскриптов: извлечение цитат, JTBD, болей»).

- Вход: `Conversation.transcript`. Выход: черновые `Insight.text` (атомарные
  цитаты/выводы, уже есть модель именно под это — «атомарные инсайты» с
  опциональной привязкой к сегменту/JTBD/разговору) — предлагаются списком
  под транскриптом на `/conversations/[id]` с кнопкой «добавить» на каждый.
  Это самая естественная точка, потому что `Insight` уже спроектирован как
  «то, что вычленяется из разговора».
  - Расширение той же обработки — предлагать JTBD/гипотезы прямо из
    транскрипта отдельного разговора, не только из профиля продукта (§2.1) —
    логичный второй шаг после того, как извлечение инсайтов уже отработано.

### 2.4 Гипотезы: приоритизация и сравнение с базой

Из ECHO-спека §10.2 («AI-генерация новых гипотез на основе базы разговоров и
JTBD», «сравнение с существующими JTBD»). Практичнее в виде двух отдельных,
более скромных функций, чем «AI придумывает гипотезы из воздуха»:

- **Дубликат-детектор.** При создании новой гипотезы (`/hypotheses/new`)
  проверка на смысловое совпадение с уже существующими `Hypothesis.statement`
  того же продукта — предупреждение, не блокировка.
- **AI-приоритизация в канбане.** Гипотезы уже двигаются по колонкам
  статуса вручную (§kanban-board.tsx); AI мог бы предлагать `priority`
  (поле уже есть в схеме, `Int?`, сейчас никак не используется UI) на основе
  количества связанных инсайтов/JTBD-уровня — не критично, но закрывает
  неиспользуемое поле схемы осмысленной функцией.

### 2.5 Дашборд «пробелов» → AI-рекомендации следующего шага

`lib/dashboard-metrics.ts` уже считает 4 вида пробелов (неподтверждённые
JTBD, сегменты без JTBD, зависшие гипотезы, продукты без свежих
исследований) — чисто механически, без интерпретации. Возможное расширение:
AI-сформулированная текстовая рекомендация «что делать дальше» под
`gaps-summary`-виджетом на основе уже посчитанных чисел (не сырых данных —
дёшево по промпту, посчитанные метрики уже готовы). Низкий приоритет:
статус-кво (голые числа со ссылками на отчёт) уже полезен, это скорее
финальная полировка, чем структурная точка.

### 2.6 Глобальный поиск → семантический слой

Сейчас `/search` — `contains`-запрос по 11 моделям (`app/search/page.tsx`),
осознанно без полнотекстового поиска (growth-plan.md §2.9: "при текущем
объёме `contains` достаточен"). AI/embeddings-поиск сюда просится только
если объём данных вырастет настолько, что буквальный `contains` перестанет
находить нужное по смыслу — то есть это триггер по объёму данных, не по
"было бы круто", и явно **не первая фаза**. Упоминается здесь для полноты
каталога, не для реализации в обозримых фазах.

### 2.7 AI-чат (из исходного спека, самый крупный и самый рискованный пункт)

ECHO §10.1 описывал чат с полным контекстом продукта. В духе «list all
possible places» — стоит явно назвать и явно отложить:

- Полноценный чат = RAG по всей базе продукта (10 моделей, потенциально
  сотни записей на активном продукте) — это по объёму работы сравнимо со
  всем остальным списком вместе взятым, и его отдача (общий Q&A) ниже, чем у
  точечных генераторов черновиков выше, которые экономят конкретное
  повторяющееся ручное действие.
- Если/когда всё-таки берётся в работу — не в MVP-фазах этого плана,
  отдельный документ.

### 2.8 Переводы / автоперевод профиля (RU → EN)

ECHO §12.4 упоминал автоперевод полей профиля продукта. Не актуально:
многоязычность интерфейса — в `plans/backlog.md` как отдельная, никак не
начатая линия, независимая от AI. Не включать, пока не появится сама задача
EN-интерфейса.

## 3. Архитектура подключения

**Одна точка выхода вовне, не размазанная по компонентам.**

```
lib/ai/
  client.ts        # тонкий HTTP-клиент к корпоративному API (fetch + токен)
  prompts.ts        # шаблоны промптов, по одному на каждую функцию §2
  types.ts          # Zod-схемы ожидаемого JSON-ответа модели, по функции
  <feature>.ts       # напр. suggestSegments.ts, suggestJtbd.ts, extractInsights.ts —
                      # каждый: собрать вход из Prisma → вызвать client → validate → вернуть Draft[]
```

- **Конфигурация:** `AI_API_URL`, `AI_API_TOKEN` в `.env`/`.env.local`,
  по аналогии с уже существующими `DATABASE_URL`/`NEXTAUTH_SECRET` в
  `.env.example`. Токен не в клиентском бандле — весь AI-код только в
  Server Actions/Route Handlers, никогда в `'use client'`.
- **Вызов — Server Action, не Route Handler,** для точек внутри существующих
  форм/визарда (тот же паттерн, что и `createXQuick` — `useTransition` на
  клиенте, никакого нового API-роута). Отдельный Route Handler оправдан
  только если понадобится стриминг ответа (не нужен для черновиков
  фиксированной структуры, о которых идёт речь в §2.1–2.4).
- **Формат ответа — строгий JSON,** проверяемый Zod-схемой на входе в
  приложение (`lib/ai/types.ts`), тем же способом, что и Zod уже проверяет
  форму FormData в каждом `lib/actions/*.ts`. Невалидный/неполный ответ
  модели → `{ ok: false, error }`, показывается как обычная ошибка формы,
  не роняет страницу.
- **Ничего не создаётся в БД напрямую AI-кодом.** `lib/ai/*.ts` возвращает
  черновики в память; фактическая запись всегда идёт через уже существующий
  `create*`/`createXQuick` Server Action, вызванный на подтверждении
  пользователя. Это даёт AI-функциям тот же аудит и то же поведение (Zod-
  валидация, `revalidatePath`, `HypothesisStatusChange`-история и т.п.)
  бесплатно, без дублирования бизнес-логики.
- **Таймауты и отказоустойчивость.** Корпоративный API — внешняя
  зависимость с непредсказуемой задержкой; каждый вызов оборачивается
  таймаутом (предлагается 15–20с — черновики не блокируют критичный путь) и
  явным `{ ok: false, error: 'AI недоступен, попробуйте позже' }` вместо
  зависшего запроса. Ни один существующий флоу (создание продукта,
  сохранение гипотезы вручную и т.д.) не должен становиться зависимым от
  доступности AI-API — AI годится только как необязательная надстройка над
  уже работающими ручными путями.

## 4. Порядок фаз (предлагаемый)

1. **Инфраструктура** — `lib/ai/client.ts` + конфигурация + одна сквозная
   тестовая функция (напр. suggestSegments) end-to-end, чтобы подтвердить
   контракт клиента/токена/таймаутов до того, как размножать по остальным
   точкам.
2. **Онбординг-мастер (§2.1)** — весь путь сегменты → JTBD → гипотезы →
   конкуренты → фичи/RTB, поскольку это один связный экран с наибольшей
   отдачей и уже готовой UI-точкой (мастер), без необходимости
   проектировать новый экран.
3. **Инсайты из разговоров (§2.3)** — второй explicit-запрошенный сценарий
   после сбора новостей; учитывая зависимость Уровня 2 от возможностей
   корпоративного API (см. §5), реалистичнее продвигается раньше §2.2
   Уровня 2.
4. **Новости по конкурентам, Уровень 1 → Уровень 2 (§2.2)** — Уровень 1
   (суммаризация вставленного текста) можно сделать сразу вслед за фазой 2
   тем же клиентом; Уровень 2 (реальный поиск) — только после ответа на
   открытый вопрос §5.
5. **Точечные улучшения** (§2.4 дубликат-детектор/приоритизация, §2.5
   AI-рекомендации на дашборде) — низкий приоритет, делать по одному, когда
   основной поток окупился.
6. **Отложено на неопределённый срок:** AI-чат (§2.7), семантический поиск
   (§2.6), автоперевод (§2.8) — см. обоснования выше.

## 5. Открытые вопросы (нужен ответ до реализации фазы 1)

- **Формат корпоративного API.** OpenAI-совместимый `/chat/completions`?
  Свой протокол? Обязателен ли structured output/JSON-mode на уровне API,
  или строгий JSON нужно вытягивать промптом и валидировать на своей
  стороне (см. §3)?
- **Есть ли у API инструмент веб-поиска/browsing?** Определяет, доступен ли
  §2.2 Уровень 2 в принципе, или сбор новостей должен остаться
  Уровнем 1 (суммаризация вставленного пользователем текста).
- **Rate limits / стоимость вызова** — влияет на то, можно ли делать
  суммарный вызов на весь мастер онбординга разом (§2.1) или нужно
  дробить по шагам с explicit-кнопкой «сгенерировать» на каждом.
- **Данные, уходящие во внешний API.** Профиль продукта и транскрипты
  разговоров — потенциально чувствительные корпоративные данные. Нужно
  подтверждение, что «локальный корпоративный API» означает вызов внутри
  периметра компании (не публичный сторонний сервис) — иначе по каждой
  точке из §2 придётся отдельно решать, можно ли ей делиться данными.

## 6. Явно вне рамок этого плана

- Отдельный AI-микросервис (Python/FastAPI) — не нужен при прямом вызове
  HTTP API из монолита.
- RAG-инфраструктура / векторная БД — не нужна, пока не понадобится
  семантический поиск (§2.6) или полноценный чат (§2.7), ни один из которых
  не в первых фазах.
- LangFuse и подобный трекинг агентов — актуально только вместе с
  многоагентной архитектурой, которой здесь нет.
- Мультиязычность / автоперевод (§2.8).
- Ролевая модель/мультитенантность — независимая, гораздо более крупная
  тема (`plans/backlog.md`), не блокирует и не блокируется этим планом.
