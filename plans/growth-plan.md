## Северная звезда

Платформа существует, чтобы: собрать всю доступную информацию о продукте → понять, какие реальные задачи (jobs) решают клиенты → связать эти задачи с сегментами, у которых они есть → подтвердить это исследованиями и разговорами → показать, где картина неполная или противоречивая, чтобы продакт-менеджер мог действовать.

Каждая фича ниже должна либо добавлять новую **связанную** информацию, либо помогать **увидеть инсайт/пробел** в уже собранной информации — не быть просто ещё одним списком CRUD.

## 1.1 Модули данных

Десять моделей в `prisma/schema.prisma`, все через `userId` (однопользовательский MVP — `where: { userId }` вручную повторяется в каждом запросе, нет workspace/org-модели):

`Product`, `Research`, `Segment`, `JTBD` (+ `JtbdSequenceEdge` для графа), `Hypothesis` (+ `HypothesisStatusChange`), `Conversation`, `Competitor`, `ProductResource`, `Feature`, `RTB`.

### Методологическое ядро: JTBD → Feature → RTB

```prisma
model Competitor {
  id          String   @id @default(cuid())
  name        String
  url         String?
  positioning String?  @db.Text
  features    String[]
  productId   String
  product     Product  @relation(fields: [productId], references: [id], onDelete: Cascade)
  userId      String
  user        User     @relation(fields: [userId], references: [id], onDelete: Cascade)
}

model Feature {
  id          String   @id @default(cuid())
  name        String
  description String?  @db.Text
  productId   String
  product     Product  @relation(fields: [productId], references: [id], onDelete: Cascade)
  userId      String
  user        User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  jtbds       JTBD[]   // many-to-many: одна фича может закрывать несколько задач
  rtbs        RTB[]    // many-to-many: фича может поддерживать несколько промо-обещаний
}

model RTB {
  id          String    @id @default(cuid())
  statement   String    @db.Text
  productId   String
  product     Product   @relation(fields: [productId], references: [id], onDelete: Cascade)
  userId      String
  user        User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  features    Feature[]
}
```

`ProductResource` — одна гибкая модель (`kind`: `SALES_KIT` / `DEVELOPER_DOC` / `CONFLUENCE_LINK` / `JIRA_LINK` / `OTHER`) вместо отдельной таблицы на тип контента; сейчас только заголовок + URL + заметка, без реальной интеграции с Confluence/Jira. Отображается как секция на странице продукта, без отдельного списка.

`Competitor`, `Feature`, `RTB` — полноценные модули (собственный список с сортировкой/CSV-экспортом, карточка, форма, копирование ссылки, "недавно просмотренное", закреплённые записи, дублирование), плюс секция на странице продукта. При первой реализации (Фаза A) были сделаны **без** `pinned`/`tags`/видимости на дашборде — по аналогии с `Product`; при последующем разборе эта аналогия признана слабой (в отличие от `Product`, эти три модуля — кросс-продуктовые списки leaf-записей, как Research/Segment/JTBD, а не корневая точка входа), и пробел закрыт — см. §2.2 "сделано".

### JTBD: иерархия, последовательность, граф, типы задач

```prisma
model JTBD {
  // ...
  parentId String?
  parent   JTBD?       @relation("JtbdHierarchy", fields: [parentId], references: [id], onDelete: SetNull)
  children JTBD[]      @relation("JtbdHierarchy")
  jobType  JtbdJobType @default(SMALL_JOB)
}

enum JtbdJobType {
  BIG_JOB    // продукт не решает полностью, часто про эмоции клиента
  CORE_JOB   // самая крупная задача, которую продукт решает целиком
  SMALL_JOB  // шаг до/после основной
  MICRO_JOB  // узкая задача внутри малой/основной
}

model JtbdSequenceEdge {
  id         String @id @default(cuid())
  fromJtbdId String
  fromJtbd   JTBD   @relation("JtbdSequenceFrom", fields: [fromJtbdId], references: [id], onDelete: Cascade)
  toJtbdId   String
  toJtbd     JTBD   @relation("JtbdSequenceTo", fields: [toJtbdId], references: [id], onDelete: Cascade)
  @@unique([fromJtbdId, toJtbdId])
}
```

- Иерархия: один родитель, произвольная глубина, дерево через `parentId`. `setJtbdParent` (`lib/actions/jtbd-graph.ts`) защищён от циклов и самоссылок (`isDescendant`).
- Последовательность: отдельный граф рёбер "следует за", независимый от уровня иерархии. `createJtbdSequenceEdge` защищён только от самоссылки — не от встречной пары (A→B и B→A одновременно) и не от циклов длиннее двух узлов. Осознанно не исправляется сейчас (см. §2.5).
- Канвас `/jtbd/graph` — `@xyflow/react` (React Flow), единственная новая зависимость сверх стандартного UI-стека. Узлы окрашены по `jobType` (легенда на канвасе), перетаскивание меняет `parentId`, соединение рёбер создаёт `JtbdSequenceEdge`, есть инлайн-добавление JTBD прямо на канвасе (`createJtbdQuick`, без редиректа), фильтр по категории. `jtbdJobTypeColors` (`lib/jtbd-job-types.ts`) — CSS-переменные темы (`--jtbd-*` в `app/globals.css`, светлая и тёмная версии), не хардкод hex (исправлено, см. §2.2).
- Обычный список `/jtbd` (группировка по категориям, % покрытия) остаётся отдельно от канваса.
- Нет валидации согласованности `jobType` с позицией в иерархии (например, ничто не мешает вложить `BIG_JOB` под `MICRO_JOB`) — осознанно не ограничивается сейчас (см. §2.5).

### Гипотезы: канбан

`/hypotheses` — карточки перетаскиваются между колонками статуса нативным HTML5 Drag and Drop (`components/hypotheses/kanban-board.tsx`, без новой зависимости), вызывает существующий `updateHypothesisStatus`, пишет в `HypothesisStatusChange`. ## 1.6 Осознанно принятые ограничения (не баги, не забытое — решения)

- **Целостность данных:** нет валидации согласованности `jobType` ↔ позиция в иерархии JTBD, нет защиты `JtbdSequenceEdge` от циклов/встречных пар, нет проверки, что `jtbdId`/`segmentId`/`researchId` гипотезы принадлежат одному продукту. - **Тесты и CI:** нет автотестов, нет `.github/workflows`. Решение продакт-менеджера (6 августа 2026): рано для этого проекта, откладывается.
- **Однопользовательский режим:** `DEFAULT_USER_ID` захардкожен, `where: { userId }` не обеспечивается общим слоем — держать в поле зрения по мере роста, не блокирует текущую работу.

## 2.1 Информационная архитектура и навигация

Вместо плоского списка из 9 пунктов (§1.3) — 5 главных табов, остальные модули становятся под-табами:

```
Продукты   Сегменты   Исследования   Маркетинг   JTBD
  │                       │           (было RTB)   │
  ├─ Конкуренты           ├─ Гипотезы               ├─ Список
  └─ Фичи                 └─ Разговоры               └─ Граф
```

- **Продукты, Сегменты, Исследования, Маркетинг, JTBD** — 5 главных табов верхнего меню. «Маркетинг» — переименование RTB для ясности (модель `RTB` в схеме может остаться как есть технически; переименовывается заголовок, ссылка в навигации и, по возможности, маршрут `/rtb` → `/marketing` — решить при реализации).
- **Конкуренты — под-таб Продуктов, привязан к конкретному продукту.** Это отдельное, специально проговорённое решение: конкурентная разведка имеет смысл только в контексте одного продукта, поэтому раздел "Конкуренты" убирается из глобальной верхней навигации и становится доступен **только** изнутри страницы продукта (аналог того, как сейчас устроены "Ресурсы"). Список конкурентов across всех продуктов сразу — не нужен.
- **Фичи — под-таб Продуктов**, но остаётся глобальным списком с фильтрами (по JTBD/сегменту, §1.1) — в отличие от Конкурентов, здесь кросс-продуктовый просмотр сохраняет ценность (сравнение фичей между продуктами). Реализуется как пункт вложенного/контекстного меню раздела "Продукты", а не как отдельный таб верхнего уровня.
- **Гипотезы и Разговоры — под-табы Исследований.** Оба тоже привязаны к продукту/исследованию, но кросс-продуктовый канбан гипотез — рабочий сценарий (сравнение пайплайна между продуктами), поэтому, в отличие от Конкурентов, глобальный список сохраняется, меняется только место в навигации.
- **JTBD — собственный главный таб** (не под-таб чего-либо ещё): это методологическое ядро платформы, поэтому получает такой же вес в навигации, как Продукты/Сегменты/Исследования/Маркетинг, а не прячется под одним из них.
- **Граф JTBD — под-таб JTBD, для быстрого доступа.** Внутри раздела JTBD — два под-таба: «Список» (группировка по категориям, % покрытия — как сейчас на `/jtbd`) и «Граф» (`/jtbd/graph`, визуальный канвас). Раньше рассматривался вариант с графом как отдельной прямой ссылкой в верхнем меню в обход списка — от него отказались в пользу explicit под-таба внутри JTBD, чтобы оба режима просмотра были на одном уровне и раздел JTBD не терялся среди остальных 4 главных табов.

**Что нужно для реализации:**
- `SiteNav` — переход от одноуровневого списка ссылок к двухуровневому (главные табы + контекстное под-меню, видимое когда активен раздел Продукты/Исследования/JTBD).
- Страница `/competitors` (глобальный список) — убрать из навигации; либо удалить маршрут совсем в пользу `/products/[id]/competitors`, либо оставить как редирект/deep-link без входа в верхнее меню. Решить при реализации, каким должен быть URL.
- Переименование RTB → "Маркетинг" в заголовках/навигации (см. §2.0 про маршрут).
- Под-навигация внутри раздела JTBD («Список» / «Граф») — вероятно, простые вкладки на странице `/jtbd`, а не полноценный контекстный дропдаун, как у Продуктов/Исследований.

## 2.4 Инсайты и связность (доп. предложения, приоритет ниже — без изменений с прошлого захода)

- **Матрица "Сегменты × JTBD"** — кросс-таблица: какой сегмент какие задачи имеет и насколько это подтверждено исследованиями.
- **Дашборд пробелов (gap analysis)** — JTBD без подтверждающего исследования, сегменты без единого JTBD, гипотезы, зависшие в "черновике", продукты без исследований за N дней.
- **Цитаты/выводы как отдельные записи** — атомарные инсайты (короткий текст + источник + привязка к сегменту/JTBD) вместо одного большого транскрипта на `Conversation`.
- **Глобальный поиск** — при 10 связанных модулях находить конкретное кликами по спискам перестаёт работать.
- **Авторизация/мультипользовательность** — не срочно, держать в поле зрения по мере роста.

## 2.5 Явно отклонённые предложения (зафиксировано, чтобы не поднимать заново)

По итогам разбора текущего состояния 6 августа 2026 продакт-менеджер явно решил **не делать сейчас**:

- Валидацию согласованности `jobType` и позиции в иерархии JTBD.
- Защиту `JtbdSequenceEdge` от циклов/встречных пар.
- Кросс-валидацию связанных записей гипотезы (`jtbdId`/`segmentId`/`researchId` из одного продукта).
- Любую другую дополнительную "жёсткость" модели данных — платформа должна оставаться гибкой на этом этапе.
- Автотесты и CI/CD — рано для текущей стадии проекта.

Причина зафиксировать явно: чтобы будущий разбор кода не поднимал эти пункты как "забытые баги" — это осознанные решения с датой.
