## Северная звезда

Платформа существует, чтобы: собрать всю доступную информацию о продукте → понять, какие реальные задачи (jobs) решают клиенты → связать эти задачи с сегментами, у которых они есть → подтвердить это исследованиями и разговорами → показать, где картина неполная или противоречивая, чтобы продакт-менеджер мог действовать.

Каждая фича ниже должна либо добавлять новую **связанную** информацию, либо помогать **увидеть инсайт/пробел** в уже собранной информации — не быть просто ещё одним списком CRUD.

## 1.1 Модули данных

Одиннадцать моделей в `prisma/schema.prisma`, все через `userId` (однопользовательский MVP — `where: { userId }` вручную повторяется в каждом запросе, нет workspace/org-модели):

`Product`, `Research`, `Segment`, `JTBD` (+ `JtbdSequenceEdge` для графа), `Hypothesis` (+ `HypothesisStatusChange`), `Conversation`, `Competitor`, `ProductResource`, `Feature`, `RTB`, `Insight` (см. §2.4).

### Методологическое ядро: JTBD → Feature → RTB

```prisma
model Competitor {
  id          String   @id @default(cuid())
  name        String
  url         String?
  positioning String?  @db.Text
  features    String[]
  productId   String
  product     Product  @relation(fields: [productId], references: [id], onDelete: Cascade)
  userId      String
  user        User     @relation(fields: [userId], references: [id], onDelete: Cascade)
}

model Feature {
  id          String   @id @default(cuid())
  name        String
  description String?  @db.Text
  productId   String
  product     Product  @relation(fields: [productId], references: [id], onDelete: Cascade)
  userId      String
  user        User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  jtbds       JTBD[]   // many-to-many: одна фича может закрывать несколько задач
  rtbs        RTB[]    // many-to-many: фича может поддерживать несколько промо-обещаний
}

model RTB {
  id          String    @id @default(cuid())
  statement   String    @db.Text
  productId   String
  product     Product   @relation(fields: [productId], references: [id], onDelete: Cascade)
  userId      String
  user        User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  features    Feature[]
}
```

`ProductResource` — одна гибкая модель (`kind`: `SALES_KIT` / `DEVELOPER_DOC` / `CONFLUENCE_LINK` / `JIRA_LINK` / `OTHER`) вместо отдельной таблицы на тип контента; сейчас только заголовок + URL + заметка, без реальной интеграции с Confluence/Jira. Отображается как секция на странице продукта, без отдельного списка.

`Competitor`, `Feature`, `RTB` — полноценные модули (собственный список с сортировкой/CSV-экспортом, карточка, форма, копирование ссылки, "недавно просмотренное", закреплённые записи, дублирование), плюс секция на странице продукта. При первой реализации (Фаза A) были сделаны **без** `pinned`/`tags`/видимости на дашборде — по аналогии с `Product`; при последующем разборе эта аналогия признана слабой (в отличие от `Product`, эти три модуля — кросс-продуктовые списки leaf-записей, как Research/Segment/JTBD, а не корневая точка входа), и пробел закрыт — см. §2.2 "сделано".

### JTBD: иерархия, последовательность, граф, типы задач

```prisma
model JTBD {
  // ...
  parentId String?
  parent   JTBD?       @relation("JtbdHierarchy", fields: [parentId], references: [id], onDelete: SetNull)
  children JTBD[]      @relation("JtbdHierarchy")
  jobType  JtbdJobType @default(SMALL_JOB)
}

enum JtbdJobType {
  BIG_JOB    // продукт не решает полностью, часто про эмоции клиента
  CORE_JOB   // самая крупная задача, которую продукт решает целиком
  SMALL_JOB  // шаг до/после основной
  MICRO_JOB  // узкая задача внутри малой/основной
}

model JtbdSequenceEdge {
  id         String @id @default(cuid())
  fromJtbdId String
  fromJtbd   JTBD   @relation("JtbdSequenceFrom", fields: [fromJtbdId], references: [id], onDelete: Cascade)
  toJtbdId   String
  toJtbd     JTBD   @relation("JtbdSequenceTo", fields: [toJtbdId], references: [id], onDelete: Cascade)
  @@unique([fromJtbdId, toJtbdId])
}
```

- Иерархия: один родитель, произвольная глубина, дерево через `parentId`. `setJtbdParent` (`lib/actions/jtbd-graph.ts`) защищён от циклов и самоссылок (`isDescendant`).
- Последовательность: отдельный граф рёбер "следует за", независимый от уровня иерархии. `createJtbdSequenceEdge` защищён только от самоссылки — не от встречной пары (A→B и B→A одновременно) и не от циклов длиннее двух узлов. Осознанно не исправляется сейчас (см. §2.5).
- Канвас `/jtbd/graph` — `@xyflow/react` (React Flow), единственная новая зависимость сверх стандартного UI-стека. Узлы окрашены по `jobType` (легенда на канвасе), перетаскивание меняет `parentId`, соединение рёбер создаёт `JtbdSequenceEdge`, есть инлайн-добавление JTBD прямо на канвасе (`createJtbdQuick`, без редиректа), фильтр по категории. `jtbdJobTypeColors` (`lib/jtbd-job-types.ts`) — CSS-переменные темы (`--jtbd-*` в `app/globals.css`, светлая и тёмная версии), не хардкод hex (исправлено, см. §2.2).
- Обычный список `/jtbd` (группировка по категориям, % покрытия) остаётся отдельно от канваса.
- Нет валидации согласованности `jobType` с позицией в иерархии (например, ничто не мешает вложить `BIG_JOB` под `MICRO_JOB`) — осознанно не ограничивается сейчас (см. §2.5).

### Гипотезы: канбан

`/hypotheses` — карточки перетаскиваются между колонками статуса нативным HTML5 Drag and Drop (`components/hypotheses/kanban-board.tsx`, без новой зависимости), вызывает существующий `updateHypothesisStatus`, пишет в `HypothesisStatusChange`. ## 1.6 Осознанно принятые ограничения (не баги, не забытое — решения)

- **Целостность данных:** нет валидации согласованности `jobType` ↔ позиция в иерархии JTBD, нет защиты `JtbdSequenceEdge` от циклов/встречных пар, нет проверки, что `jtbdId`/`segmentId`/`researchId` гипотезы принадлежат одному продукту. Решение продакт-менеджера (6 августа 2026): не усложнять сейчас — платформа не должна быть слишком строгой на этом этапе.
- **Тесты и CI:** нет автотестов, нет `.github/workflows`. Решение продакт-менеджера (6 августа 2026): рано для этого проекта, откладывается.
- **Однопользовательский режим:** `DEFAULT_USER_ID` захардкожен, `where: { userId }` не обеспечивается общим слоем — держать в поле зрения по мере роста, не блокирует текущую работу.

## 2.3 Карточная перегруппировка: Конкуренты, Фичи, Маркетинг — ✅ сделано

Списки `/competitors`, `/features`, `/marketing` были плоской сеткой карточек по всем продуктам сразу — самый "плоский" паттерн из оставшихся на платформе (в отличие от `/jtbd`, который уже группировал по категории). Приведены к тому же принципу, что и `/jtbd`: **группировка по продукту**, а не по абстрактным зонам-разделам (как на странице продукта, §1.2) — этим трём модулям, в отличие от Product, зонирование не подходит, это списки leaf-записей, а не аггрегатор с несколькими смысловыми блоками.

### D.3 Мастер настройки нового продукта — как реализовано

4. **Гипотезы** (`hypotheses`) — «Что вы предполагаете?», с привязкой к JTBD и сегменту
5. **Конкуренты** (`competitors`) — «С кем вы конкурируете?»
6. **Фичи и RTB** (`features`) — «Что вы предлагаете и почему это должны купить?», две под-секции: Фичи (с чекбоксами JTBD) → RTB (с чекбоксами фич)

**Осознанное упрощение (не было заранее согласовано с продакт-менеджером, фиксируем явно):** списки шагов мастера — только добавление, без инлайн-удаления. Каждый существующий `delete*` action (`deleteSegment`, `deleteInsight` и т.д.) вызывает `redirect()`, что сломало бы поток мастера (страница должна остаться на месте) — заводить неперенаправляющие "быстрые удаления" для 9 моделей ради мастера сочли избыточным объёмом для этой итерации. Убрать/поправить запись, добавленную по ошибке в мастере, можно только после — через обычный UI редактирования/удаления соответствующего раздела.

## 2.7 Визуальная идентичность: «Реестр» — ✅ сделано целиком (план утверждён и реализован 7 августа 2026)

### Критика текущего состояния

Сегодняшний UI — стандартный набор shadcn/ui поверх slate base color с одной заменой акцента на красный: один шрифт (Inter) на всё — заголовки, тело, кнопки, бейджи, числа; карточка — единственный структурный приём, применяется одинаково к статистике на дашборде, элементам списка и сгруппированным секциям. Пять плиток дашборда («Гипотезы», «Разговоры», «Конкуренты»...) визуально неразличимы — одинаковый вес числа, одинаковый серый лейбл, никакого цветового или размерного сигнала о том, что важнее. Канбан гипотез (Черновик/На проверке/Подтверждена/Опровергнута) не использует цветовую кодировку статуса, хотя это буквально пайплайн. Заголовки карточек в списках (Конкуренты, Фичи) обрезаются посреди слова без tooltip. На разреженных страницах (Конкуренты, Фичи) под парой карточек остаётся стена пустого места. Анимации и hover-эффектов нет вообще.

При этом в кодовой базе уже есть два подлинно самобытных приёма, которые нигде не используются за пределами одного места: 4-цветная таксономия типов JTBD (big/core/small/micro — фиолетовый/красный/синий/серый, `--jtbd-*` в `globals.css`), и сквозная нумерация записей (`#31 Опросник для оценки...`, `#30 Квалификационные интервью...` — Prisma `@default(autoincrement())` на `number`), которая сейчас проявляется только как случайный «#» перед заголовком.

Вывод: это узнаваемый generic admin-dashboard вид с заменённым акцентом, а не осознанная идентичность.

### Направление: «Реестр»

Задача RPM — превращать разговоры с клиентами в пронумерованные типизированные утверждения (JTBD, гипотезы, RTB), каждое со статусом и уровнем уверенности. Это картотека доказательств, а не обобщённый CRUD. Направление опирается ровно на два уже существующих в коде приёма — нумерацию записей и цветовую таксономию JTBD — и делает их сквозным визуальным языком приложения вместо разового элемента графа.

**Цвет** (красно-белая корпоративная идентичность — уже принятое ранее решение, не меняется; формализуется то, что уже неявно есть):
- `--ink` `#1C1917` — тёплый почти-чёрный для текста
- `--paper` `#FFFFFF` — без изменений
- `--brand-red` `#D9291F` — без изменений, `--primary`
- `--signal-violet` `#6D28D9` — большая задача / высокая уверенность
- `--signal-blue` `#2554D6` — малая задача / в процессе
- `--signal-slate` `#52606D` — микрозадача / нейтральный статус

Последние три уже существуют как `--jtbd-*` — это не новая палитра, а повышение существующего решения до статуса сквозного языка приложения.

**Типографика** — три роли вместо одной:
- **Manrope** (display) — заголовки, врезки секций, wordmark в шапке. Геометричный, более характерный, чем Inter, полная поддержка кириллицы.
- **Inter** (body) — остаётся как есть: формы, параграфы, кнопки. Уже подключён (`app/layout.tsx`), трогать незачем.
- **IBM Plex Mono** (utility) — номера записей (`#031`), статус-бейджи, протокольные/нормативные строки, которые и так естественно встречаются в этом домене (CMP/EST/ACME/WSTEP, Приказ №117 ФСТЭК). Это не декоративный выбор — контент уже технический/кодифицированный, моно-шрифт делает его читаемым вместо того, чтобы растворять в Inter.

**Layout** — тот же каркас карточной сетки (верно для плотного CRUD-инструмента), но с уточнениями:
```
[эйбрау: #031 · ИССЛЕДОВАНИЕ]     ← моно, цвет сигнала
Заголовок записи                   ← Manrope
Тело на Inter…
```
Заголовки секций везде (не только на странице продукта) получают уже существующую в одном месте красную полосу-индекс. Колонки канбана и статус-бейджи гипотез получают сигнальные цвета. Плитки дашборда перегруппировываются по образцу собственного деления страницы продукта («Исследование клиентов» / «Позиционирование») вместо одной недифференцированной сетки 5×1.

**Сигнатура:** пара «номер реестра + сигнальный цвет», применённая последовательно везде, где отображается запись — список, карточка, канбан, узел графа, бейдж — так что с одного взгляда понятен и тип записи, и её стадия/уверенность, без чтения лейбла.

**Проверка на «типовые AI-паттерны»:** не тёплый кремовый + serif, не почти-чёрный + неон, не broadsheet-газетная сетка с hairline-линиями. Палитра остаётся бело-красной, потому что это реальное, ранее принятое решение продукта — самобытность идёт от формализации уже существующей таксономии, а не от импорта тренда.

### Найденные баги

**Счётчики на дашборде показывают 0 при наличии реальных данных — ✅ исправлено.** Причина подтверждена (гипотеза из первой версии этого плана оказалась верна, но не в той части, что ожидалось): дело не в ошибке гидратации где-то ещё на странице, а в самом `<CountUp>`. Компонент использовал `useRef`-флаг `started`, чтобы не перезапускать анимацию — но под React 18 Strict Mode (включён в `next.config.js`, эффекты в dev-режиме выполняются mount → cleanup → mount) первый вызов эффекта успевал запланировать `requestAnimationFrame`, который тут же отменялся симулированным cleanup-ом до первой отрисовки кадра, а повторный вызов эффекта видел `started.current === true` и не запускал анимацию заново — счётчик так и оставался на исходном «0» из `useState(0)`. В продакшен-сборке эта проблема не проявляется (Strict Mode не дублирует эффекты вне dev-режима), поэтому она не всплыла в релизной QA (§2.8), которая тестировалась именно на `next build && next start`. Исправление — `components/shared/count-up.tsx`: убран ref-флаг, эффект просто перезапускается безопасно (повторный `cancelAnimationFrame` на уже отменённый/отработавший кадр — no-op). Проверено вживую в dev-режиме: счётчики теперь показывают реальные значения (1, 4, 9, 6, 5, 3, 3, 2, 4, 3 на демо-продукте) в течение ~0.5с после загрузки.

**Граф JTBD теряет расстановку узлов при любом редактировании — ✅ исправлено (7 августа 2026, Фаза 2).** Причина была найдена точно: `layoutTree()` в `components/jtbd-graph/canvas.tsx` пересчитывала позиции всех узлов заново при каждой загрузке графа, исходя только из текущей структуры родитель/потомок, и нигде не сохраняла результат — `useNodesState` держал позицию только в памяти браузера на время сессии. Решение — §2.9.1, персистентные позиции по представлению + раздельные графы по сегментам.

### 2.9.1 Персистентные позиции узлов + отдельные графы по сегментам — ✅ сделано (7 августа 2026)

Реализован выбранный вариант (подтверждён продакт-менеджером): не просто запоминать позиции, а завести полноценные независимые графы — общий и по каждому сегменту, с раздельной раскладкой в каждом.

- **Схема:** новая таблица `JtbdGraphLayout` — `(jtbdId, viewKey, x, y)`, уникальный индекс на `(jtbdId, viewKey)`, `onDelete: Cascade` от `JTBD`. `viewKey` — `"overall"` (константа `OVERALL_VIEW_KEY` в `lib/jtbd-graph-layout.ts`) для общего графа или `id` сегмента для графа конкретного сегмента. Один и тот же JTBD может иметь разные координаты в разных представлениях — подтверждено вживую: перетаскивание узла в общем графе не повлияло на его позицию в графе сегмента, и наоборот.
- **JTBD ↔ Сегмент теперь многие-ко-многим** (было — одиночный опциональный `segmentId` на JTBD). Миграция выполнена через `prisma db push --accept-data-loss` с ручным переносом данных: все 6 существующих связей `JTBD.segmentId` сохранены в бэкап перед пушем схемы и восстановлены в новую implicit-M2M таблицу `_JTBDToSegment` через raw SQL сразу после — проверено `SELECT`-ом, что все 6 связей на месте, потерь не было. `Hypothesis`, `Insight`, `Conversation` не затронуты — у них остались собственные независимые `segmentId`, не производные от JTBD.
- **Иерархия и последовательность остались глобальными**, как и планировалось — связь «родитель → потомок» и «следует за» не зависит от представления. Меняются только видимость узла (виден только если привязан к сегменту текущего представления, либо это общий граф) и его координаты. Существовавшая фильтрация рёбер (рисуются только если оба конца видны в текущем наборе узлов) не потребовала изменений — она уже работала по нужному принципу.
- **UI:** переключатель представления на странице графа (`components/forms/jtbd-graph-filter-form.tsx`, между фильтром продукта и фильтром категории) — «Общий граф» + список сегментов продукта, auto-submit по `onChange`, как и остальные фильтры на этой странице. Форма JTBD (`components/forms/jtbd-form.tsx`) и шаг мастера онбординга (`components/onboarding/jtbd-step-form.tsx`) получили мультивыбор сегментов (чекбоксы, по образцу мультивыбора JTBD/RTB на форме Фичи) вместо одиночного select. Создание нового JTBD прямо на канвасе (обе панели — с кнопкой и пустое состояние) внутри графа конкретного сегмента передаёт `segmentIds: [текущий segmentId]` в `createJtbdQuick` — новая задача сразу привязывается к открытому сегменту.
- **Сохранение позиции:** страница графа (`app/jtbd/graph/page.tsx`, Server Component) при каждой загрузке подгружает существующие `JtbdGraphLayout` для текущего `viewKey`, и для любого видимого JTBD без сохранённой позиции сразу считает её через `layoutTree()` и делает upsert в транзакции («запись при чтении») — так что уже с первого открытия представления позиция «прилипает» и не пересчитывается заново. При отпускании узла после перетаскивания (`onNodeDragStop`, случай без пересечения с другим узлом — пересечение по-прежнему означает «сделать дочерним», как раньше) вызывается Server Action `saveJtbdGraphPositions` (`lib/actions/jtbd-graph.ts`), которая делает upsert без `router.refresh()` — позиция уже в локальном состоянии React Flow, лишний повторный рендер не нужен.
- **Кнопка «Автоматически расставить»** — новая панель `top-right` на канвасе, пересчитывает позиции всех узлов текущего представления через `layoutTree()`, сразу обновляет локальный `nodes` state и персистит результат тем же `saveJtbdGraphPositions`.
- **Пересчитаны все места, читавшие одиночную связь:** матрица «Сегменты × JTBD» (`/reports/segments-jtbd`) — JTBD без сегментов по-прежнему считается в строке «Без сегмента», а JTBD с несколькими сегментами теперь корректно учитывается в каждой из соответствующих строк; фильтр по сегменту на странице Фич (`app/features/page.tsx`); дашборд пробелов (`/reports/gaps`) не читал `segmentId` напрямую и правок не потребовал.

Проверено вживую (Playwright, dev-режим, демо-продукт «Рутокен CLM», 6 JTBD): открытие общего графа и графа отдельного сегмента показывает независимые наборы узлов; перетаскивание узла в открытое пространство холста меняет и сохраняет его координаты (подтверждено запросом к `JtbdGraphLayout` и тем, что позиция пережила `page.reload()`); кнопка «Автоматически расставить» возвращает узел к рассчитанной позиции и тоже персистит её; создание JTBD с несколькими сегментами через полную форму и через шаг мастера корректно отражается на карточке (обе метки сегмента показаны) и в форме редактирования (оба чекбокса предзаполнены); матрица «Сегменты × JTBD» и фильтр Фич по сегменту не выдают ошибок и корректно учитывают многосегментный JTBD. Самая широкая по охвату часть плана (9 моделей), но самая низкая по риску на одно изменение — не меняет модель данных, чисто аддитивный UI-паттерн.

## Открытые вопросы на будущее (не блокируют старт)

- Feature ↔ RTB: точная семантика many-to-many устраивает, или RTB должен быть привязан к одной конкретной фиче?
- Нужен ли на канвасе JTBD отдельный "read-only" режим, или редактирование всегда доступно всем, у кого есть доступ к платформе?
- Confluence/Jira: когда реальная интеграция станет актуальна — OAuth от лица пользователя или сервисный аккаунт на весь workspace?
- Массовый ввод (D.4): достаточно ли простого формата "одна запись на строку", или сразу нужна поддержка CSV с несколькими колонками?
- Мастер нового продукта (D.3): стоит ли добавить неперенаправляющие "быстрые удаления" в шаги мастера, если append-only список окажется неудобным на практике?
- Тёмная тема: токены полностью рабочие и проверены (§2.7 фаза 3), но переключателя (авто по `prefers-color-scheme` или ручной) в интерфейсе по-прежнему нет — заводить его сейчас или ждать отдельного запроса?
- Мобильная навигация (найдено в §2.8): на ширине 375px верхнее меню не переносится и не сворачивается в гамбургер — пункты доступны через горизонтальный скролл шапки, ничего не теряется, но UX не идеален. Стоит ли делать полноценное мобильное меню, и если да — гамбургер или что-то другое?
- Конкурент, доп. атрибуты (§2.9.4): точный состав дополнительных полей карточки конкурента не зафиксирован, предложен только стартовый набор (дата последней проверки, модель ценообразования, размер компании) — нужен ли он именно такой, или список должен быть другим?
- Граф по сегментам, невидимые узлы (§2.9.1): при открытии графа конкретного сегмента ребро к узлу, привязанному к другому сегменту, по умолчанию не рисуется вовсе (узел не входит в текущее представление). Устроит ли это на практике, или нужно показывать такие узлы полупрозрачными/неактивными, чтобы не терять контекст иерархии?
