# План: 5 представлений платформы (PM / CPO / компания / маркетинг / продажи)

Статус: в разработке на ветке `2.0` (см. `git tag v1.0` для точки, откуда
она стартовала). Фаза 0 сделана — см. §8. Остальные фазы не реализованы.
Составлено по запросу — пять
разных ролей должны видеть RPM Platform по-разному: обычный PM (свои 3–4
продукта + команда + процессы + роадмап), CPO (все продукты как экосистема),
открытый дашборд компании, маркетинг-инструменты, быстрый доступ для продаж.
Это самый крупный запрос за всю историю проекта — фактически превращает
однопользовательский инструмент одного PM в инструмент отдела продукта на
компанию, поэтому перед написанием плана были заданы уточняющие вопросы;
зафиксированные ответы — основа архитектуры ниже.

## 0. Зафиксированные решения (из уточняющих вопросов)

1. **Глубина авторизации в этой фазе — имитация, не настоящий RBAC.**
   Переключатель «посмотреть как PM / CPO / маркетинг / продажи» поверх уже
   существующих единых данных (`DEFAULT_USER_ID`), без переписывания
   NextAuth-флоу под пять ролей. Настоящее разграничение доступа — то, когда
   PM физически не может увидеть чужие продукты — сознательно отложено до
   отдельной, более поздней фазы (см. §7 «Вне рамок»). Исключение —
   открытый дашборд компании (см. пункт 3 ниже): он строится по-настоящему,
   без логина, потому что по смыслу запроса обязан быть таким с самого
   начала.
2. **«Люди», которым PM делегирует задачи, — лёгкие карточки-справочник,
   не логин-аккаунты.** Новая модель `Person` (имя, роль/должность,
   команда, аватар) — того же типа запись, что и `Competitor` сегодня:
   есть, чтобы на неё ссылаться и её показывать, не для входа в систему.
3. **Роадмап — отдельная новая модель**, не поле у `Feature`. Пункт
   роадмапа — это не всегда «фича, которую уже строим» (может быть ставка,
   эксперимент, этап исследования), поэтому он ссылается на `Feature`
   опционально, а не обязан быть с ней тем же самым.
4. **Диаграмма процессов/делегирования — отдельная новая модель
   (`ProcessStep`/`ProcessEdge`), которая переиспользует только канвас**
   (React Flow + авторасстановка + сохранение позиций — уже проверенная в
   графе JTBD инфраструктура), не данные JTBD. JTBD остаётся про «какую
   задачу клиента мы решаем»; процесс — про «кто что делает внутри
   команды» — разные домены, смешивать модели не стоит даже ради экономии
   кода.

## 1. Новые модели данных (черновой набросок Prisma)

```prisma
// Лёгкая карточка человека — не логин-аккаунт (см. §0.2)
model Person {
  id        String   @id @default(cuid())
  name      String
  role      String?      // свободный текст должности, напр. "Маркетинг-лид"
  team      String?      // свободная группировка, напр. "Продукт", "Маркетинг"
  email     String?      // только для отображения, не для входа
  avatarUrl String?
  skills    String[]     // тот же паттерн тегов, что уже используется у 6 моделей
  pinned    Boolean  @default(false)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  userId String
  user   User @relation(fields: [userId], references: [id], onDelete: Cascade)

  ownedProducts Product[]      @relation("ProductOwner")
  roadmapItems  RoadmapItem[]
  processSteps  ProcessStep[]
}
```

```prisma
// Product получает поле «ответственный PM» — отдельно от userId
// (userId — это тенант/создатель записи в текущей однопользовательской
// модели, ownerId — это то, кто из персонажей-Person реально ведёт продукт;
// разные оси, их нельзя схлопывать в одну).
model Product {
  // ...существующие поля без изменений...
  ownerId       String?
  owner         Person?  @relation("ProductOwner", fields: [ownerId], references: [id], onDelete: SetNull)
  publicSummary String?  @db.Text // клиентская фраза "что продукт делает для клиента" для открытого дашборда (§4); пусто — на публичной странице падаем на обрезанный `description`
}
```

```prisma
enum RoadmapStatus {
  PLANNED
  IN_PROGRESS
  SHIPPED
  PAUSED
}

enum RoadmapVisibility {
  INTERNAL
  PUBLIC
}

model RoadmapItem {
  id          String            @id @default(cuid())
  title       String
  description String?           @db.Text
  status      RoadmapStatus     @default(PLANNED)
  quarter     String?           // свободный текст "2026 Q3" — не date-range picker,
                                  // пока реальное использование не покажет, что формат нужен точнее
  visibility  RoadmapVisibility @default(INTERNAL)
  pinned      Boolean           @default(false)
  createdAt   DateTime          @default(now())
  updatedAt   DateTime          @updatedAt

  productId String
  product   Product @relation(fields: [productId], references: [id], onDelete: Cascade)

  ownerId String?
  owner   Person? @relation(fields: [ownerId], references: [id], onDelete: SetNull)

  featureId String?             // опционально — не каждый пункт роадмапа уже фича
  feature   Feature? @relation(fields: [featureId], references: [id], onDelete: SetNull)

  jtbdId String?
  jtbd   JTBD? @relation(fields: [jtbdId], references: [id], onDelete: SetNull)

  userId String
  user   User @relation(fields: [userId], references: [id], onDelete: Cascade)
}
```

```prisma
// Процесс — один канонический флоу на продукт (в отличие от JTBD-графа
// с раскладкой на представление — тут не нужна вариативность "по сегменту",
// у внутреннего процесса нет сегментов).
model ProcessStep {
  id        String   @id @default(cuid())
  title     String       // напр. "PM планирует кампанию", "Обсуждение с маркетингом"
  x         Float
  y         Float
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  productId String
  product   Product @relation(fields: [productId], references: [id], onDelete: Cascade)

  assignedPersonId String?
  assignedPerson   Person? @relation(fields: [assignedPersonId], references: [id], onDelete: SetNull)

  edgesFrom ProcessEdge[] @relation("ProcessFrom")
  edgesTo   ProcessEdge[] @relation("ProcessTo")
}

model ProcessEdge {
  id         String   @id @default(cuid())
  fromStepId String
  fromStep   ProcessStep @relation("ProcessFrom", fields: [fromStepId], references: [id], onDelete: Cascade)
  toStepId   String
  toStep     ProcessStep @relation("ProcessTo", fields: [toStepId], references: [id], onDelete: Cascade)
  label      String?     // напр. "передаёт в", "согласовывает с"
  createdAt  DateTime    @default(now())

  @@unique([fromStepId, toStepId])
}
```

```prisma
// CPO-экосистема (§5): корреляции между продуктами сначала считаются "на
// лету" из уже существующих связей (общие сегменты/категории JTBD) — без
// новой модели. Эта модель — только для *ручной* пометки CPO "вот тут я
// вижу возможность интеграции", когда автоматика недостаточна. Добавляется
// в Фазе 5, не раньше — не строить впрок то, что можно вывести запросом.
model ProductOpportunity {
  id         String   @id @default(cuid())
  productAId String
  productA   Product  @relation("OpportunityA", fields: [productAId], references: [id], onDelete: Cascade)
  productBId String
  productB   Product  @relation("OpportunityB", fields: [productBId], references: [id], onDelete: Cascade)
  note       String   @db.Text
  createdAt  DateTime @default(now())

  userId String
  user   User @relation(fields: [userId], references: [id], onDelete: Cascade)
}
```

```prisma
// Быстрые экшн-планы на предсказуемые "пожары" (§3) — обоснование в
// plans/pm-time-allocation-research.md §1: 52% времени PM уходит на
// незапланированное реагирование (ProductPlan, State of Product Management).
// Не система инцидент-менеджмента — просто заранее написанный "что делать",
// чтобы в моменте не тратить время на придумывание реакции с нуля.
model ActionPlan {
  id        String   @id @default(cuid())
  scenario  String   // "Клиент публично жалуется в соцсетях", "Конкурент резко снизил цену"
  trigger   String?  @db.Text // как понять, что сценарий наступил
  steps     String[] // упорядоченный список коротких шагов — Postgres-массив
                       // сохраняет порядок вставки, тот же паттерн, что и
                       // Competitor.features
  tags      String[] // свободные категории ("PR-кризис", "срыв дедлайна") —
                       // тот же паттерн тегов, что у 6 других моделей
  pinned    Boolean  @default(false)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  productId String
  product   Product @relation(fields: [productId], references: [id], onDelete: Cascade)

  ownerId String?             // кто координирует реакцию по этому сценарию
  owner   Person? @relation(fields: [ownerId], references: [id], onDelete: SetNull)

  processStepId String?       // опционально — к какому шагу процесса относится
  processStep   ProcessStep? @relation(fields: [processStepId], references: [id], onDelete: SetNull)

  userId String
  user   User @relation(fields: [userId], references: [id], onDelete: Cascade)
}
```

Итого 6 новых моделей (`Person`, `RoadmapItem`, `ProcessStep`, `ProcessEdge`,
`ActionPlan`, `ProductOpportunity` — последняя опциональная, Фаза 5) + 2
новых поля на `Product` (`ownerId`, `publicSummary`).

## 2. Механика «переключателя ролей» (раз авторизация — имитация)

Раз реальных ролей нет, нужен явный, понятный самому себе механизм, а не
незаметная подмена данных:

- Компонент-переключатель в `SiteNav` (рядом с переключателем темы,
  тот же паттерн — маленькая кнопка/дропдаун, состояние в `localStorage`
  через `lib/client-storage.ts`, как и всё остальное персональное в этом
  приложении).
- Четыре персонажных раздела — **отдельные топ-уровневые роуты**
  (`/pm`, `/cpo`, `/marketing`, `/sales`), не query-параметр поверх
  существующих 10 CRUD-разделов: макеты у персонажей принципиально разные
  (PM видит хаб на один продукт; CPO — кросс-продуктовый обзор), это не
  один и тот же экран с другим фильтром.
- Открытый дашборд компании (§4) — **пятый, отдельный публичный роут**
  (`/public`, без входа в переключатель) — по смыслу именно он должен быть
  ссылкой, которую можно скинуть в общий чат компании без объяснений.
- **Явная оговорка, которая должна быть видна и в UI, не только в этом
  документе:** сегодня `/pm`, `/cpo`, `/marketing`, `/sales` доступны
  любому, кто открыл приложение — переключатель ролей это способ
  посмотреть на данные под нужным углом, а не граница доступа. Настоящее
  разграничение («этот PM физически не увидит чужой продукт») — предмет
  отдельной фазы, см. §7.

## 3. PM-представление (`/pm`)

Скоуп на один выбранный продукт за раз (у PM обычно 3–4 — простой
переключатель продукта наверху страницы, тот же паттерн, что уже есть в
`SiteNav`'е поиска). Компоненты:

- **Хаб продукта** — сокращённая версия уже существующей страницы
  `/products/[id]`, с acknowledgement, что сегменты не обязательны (это уже
  и так true в текущей схеме — `Segment` не требует ничего от `Product`
  кроме связи, здесь ничего нового делать не нужно, только явно не
  требовать их наличия в UI PM-хаба).
- **Роадмап продукта** — список/таймлайн `RoadmapItem` по кварталам
  (`quarter`), с бейджем статуса (тот же визуальный паттерн, что и статусы
  гипотезы — `hypothesisStatusTone`/`Icon` уже есть, `roadmapStatusTone`
  добавляется по аналогии), опциональной ссылкой на `Feature`/`JTBD`,
  ответственным `Person`. Создание/редактирование — обычная форма
  (`lib/actions/roadmap.ts`, тот же CRUD-паттерн, что у всех 11 моделей).
- **Командный дашборд / матрица делегирования** — таблица `Person`
  (отфильтрованных по продукту через их активные `RoadmapItem`/
  `ProcessStep`) × их текущая нагрузка (сколько активных пунктов роадмапа
  и шагов процесса на них назначено прямо сейчас). Это делает дашборд
  реально «кто что делает» вместо голого списка контактов — без роадмапа
  из Фазы 1 эта страница была бы пустой визиткой, поэтому роадмап идёт
  раньше в порядке фаз (§8).
  - **Открытый вопрос:** пользователь описал это как «стратегическую
    матрицу» — не уточнено, какие именно оси. Предложенный по умолчанию
    вариант выше (человек × текущая нагрузка) — самый дешёвый в реализации
    и опирается только на уже спроектированные модели; если нужна другая
    ось (напр. компетенция/грейд × доступность), это меняет `Person`
    (например, добавляет структурированное поле уровня вместо/вместе с
    `skills`), но не меняет остальную архитектуру — можно уточнить перед
    Фазой 2, не раньше.
- **Диаграмма процесса** — канвас на базе `ProcessStep`/`ProcessEdge`,
  переиспользующий инфраструктуру `components/jtbd-graph/canvas.tsx`
  (React Flow, drag, кнопка авторасстановки) в новом
  `components/process-graph/`. В отличие от JTBD-графа — один канонический
  layout на продукт (позиция сохраняется прямо на `ProcessStep.x/y`, без
  аналога `JtbdGraphLayout` по представлениям — у процесса нет сегментов,
  вариативность не нужна). Пример из запроса («PM планирует → обсуждает с
  маркетингом → передаёт в PR») — узел = `ProcessStep` с `assignedPerson`,
  ребро = `ProcessEdge` с необязательной подписью действия.
- **Быстрые экшн-планы на непредвиденные ситуации.** Прямое обоснование —
  `plans/pm-time-allocation-research.md` §1: 52% времени PM уходит на
  незапланированное «тушение пожаров» (ProductPlan, State of Product
  Management), а не на заранее продуманную реакцию. `ActionPlan` (см. §1) —
  заранее написанный «если случилось X → команда делает 1, 2, 3, ответственный
  — Y» для предсказуемо повторяющихся нештатных ситуаций (клиент публично
  жалуется, конкурент резко снижает цену, срывается дедлайн релиза,
  критический баг в проде). Смысл не в том, чтобы описать вообще все
  возможные кризисы — а в том, чтобы **для нескольких самых вероятных**
  команда тратила на реакцию минуты («открыл готовый план, назначил
  ответственного, разослал шаги»), а не заново придумывала процесс в
  моменте, под давлением времени. Отображается двумя способами: (а)
  отдельный список экшн-планов продукта — для быстрого доступа именно в
  момент «пожара», это не тот момент, когда у PM есть время искать что-то
  на канвасе; (б) иконка-счётчик на узле диаграммы процесса, если у шага
  есть привязанные планы («что делать, если этот конкретный шаг пошёл не
  так») — контекстная находка для тех, кто разглядывает сам процесс, а не
  срочный доступ. Список (а) — основной путь, (б) — вторичный.

## 4. Открытый дашборд компании (`/public`, без входа)

Самая чувствительная с точки зрения данных часть — единственное место,
которое реально общедоступно, поэтому нужен явный **список того, что можно
показывать** (белый список полей), а не «показать всё, кроме»:

**Можно показывать:**
- Список продуктов: `Product.name`, `Product.stage`, `Product.publicSummary`
  (или обрезанный `description`, если пусто), имя и роль `owner` (`Person`).
- `RoadmapItem`, только там где `visibility = PUBLIC` — заголовок, статус,
  квартал. **Без описания** по умолчанию (описание пункта роадмапа обычно
  содержит внутренние детали реализации, даже если сам факт «планируется X»
  безопасен публично) — если понадобится показывать описание, это
  отдельное решение по каждому пункту, не общий переключатель.

**Нельзя показывать ни при каких обстоятельствах** (явно фиксируется здесь,
чтобы не решать это ситуативно в коде каждой отдельной страницы):
`Research`/`Conversation` (транскрипты клиентов), `Insight`, `Hypothesis`,
`Competitor` (конкурентная разведка — данные о конкурентах не для внешнего
и внутрикорпоративного открытого распространения тоже), внутренние
`RoadmapItem` (`visibility = INTERNAL`), `ProcessStep`/`ProcessEdge`
(внутренняя кухня команды), `ProductOpportunity` (стратегические заметки
CPO).

**Технически:** отдельный публичный Server Component без проверки сессии
(её и так нет ни у кого сегодня, но публичный роут должен быть написан так,
будто она появится завтра — запросы явно `select`-ят только перечисленные
поля, а не берут модель целиком и не полагаются на то, что чувствительные
поля «просто не отрендерятся» в JSX). Это первое место в приложении, где
разница между «поле не показано в UI» и «поле не запрошено у БД» реально
имеет значение для безопасности, а не только для производительности.

## 5. CPO-представление (`/cpo`)

- **Все продукты, обзорная сетка** — переиспользует `ModuleRail`-подобный
  паттерн, но по продуктам, не по разделам одного продукта.
- **Экосистема / корреляции.** Сначала — вычисляемые (не хранимые)
  пересечения: продукты, у которых есть сегменты с одинаковым/похожим
  `Segment.name`, или JTBD с общей `category` — простой `groupBy`-запрос
  того же типа, что уже есть в `lib/dashboard-metrics.ts`, просто без
  фильтра по одному продукту. `ProductOpportunity` (см. §1) добавляется
  только если автоматических пересечений недостаточно, чтобы CPO мог
  зафиксировать словами возможность, которую формулы не увидят — это
  сознательно вынесено в отдельную, более позднюю фазу (§8, Фаза 5),
  чтобы не строить ручную аннотацию раньше, чем понятно, нужна ли она
  вообще поверх автоматики.
  - **Открытый вопрос:** «похожесть» сегментов/категорий по точному
    совпадению имени — грубый критерий (разные PM могут по-разному назвать
    один и тот же сегмент). Более умный вариант (общие теги, fuzzy-match)
    можно добавить позже — предложено начать с точного совпадения, потому
    что это ноль новой инфраструктуры и уже покажет, полезна ли сама идея.
- **Ключевые направления развития** — кросс-продуктовая версия уже
  существующего `getGapsCounts`/`getHypothesisStatusCounts` (`lib/
  dashboard-metrics.ts`) — те же 4 «пробела» и воронка гипотез, но
  агрегированные по всем продуктам сразу с разбивкой по продукту, плюс
  разбивка `RoadmapItem` по статусу на продукт (сколько в работе, сколько
  запланировано, сколько зависло в `PLANNED` неоправданно долго — тот же
  принцип «зависшая гипотеза 14+ дней», перенесённый на роадмап).
- **Мультипродуктовый роадмап** — тот же `RoadmapItem`, но без фильтра по
  продукту, сгруппированный по кварталу с продуктом как второй осью —
  визуально таблица «квартал × продукт», не таймлайн одного продукта.

## 6. Маркетинг-инструменты (`/marketing-hub`, чтобы не путать с уже
существующим `/marketing` — CRUD-разделом RTB)

Наименее рискованная часть плана: почти вся нужная информация уже есть в
существующих моделях, это по сути новая read-only страница-компоновка
поверх уже собранных данных, без новой схемы (кроме использования
`RoadmapItem` для «что скоро выходит»):

- Фильтр по сегменту → показывает: какие `JTBD` этого сегмента подтверждены
  исследованием, какие `Feature` их закрывают, какие `RTB` опираются на эти
  фичи — то есть готовый «а что мы вообще можем сказать клиентам этого
  сегмента» без ручного пролистывания трёх разделов.
- Отдельная лента «скоро» — `RoadmapItem` со статусом `IN_PROGRESS`/
  `PLANNED`, чтобы маркетинг видел, что скоро можно будет анонсировать,
  до того как это стало `SHIPPED` фичей.

## 7. Продажи (`/sales-hub`)

Тоже почти без новой схемы — уже существующие `ProductResource` (sales-kit,
слайды) и `Feature` дают почти всё нужное; `RoadmapItem` закрывает
недостающий кусок «фичи ещё нет, но она запланирована»:

- Быстрый вход по продукту → сразу список `ProductResource` (kind =
  `SALES_KIT` в первую очередь, остальные ниже).
- Поиск «есть ли у нас фича X» — расширение уже существующего глобального
  `contains`-поиска (`app/search/page.tsx`) на `Feature` и `RoadmapItem`
  сразу, с явной пометкой в результате: «уже есть» (`Feature` существует)
  vs. «запланировано на 2026 Q3, статус: в работе» (`RoadmapItem`, если
  подходящей `Feature` ещё нет) vs. «не найдено» — три разных ответа на
  один и тот же вопрос продажника, каждый требует разного следующего шага
  с клиентом.
  - **Открытый вопрос дизайна:** показывать точную дату/квартал продажнику
    напрямую рискованно (квартал легко превращается в обещание клиенту) —
    альтернатива: показывать только качественный статус («в работе» /
    «запланировано» / «пока не в планах») без даты, а точный квартал —
    только во внутренних `/pm`/`/cpo` представлениях. Предложено как
    дефолт, требует подтверждения перед Фазой 7.

## 9. Явно вне рамок этого плана

- **Настоящая многопользовательская авторизация с разграничением доступа
  по ролям** (PM физически не видит чужие продукты, маркетинг не может
  редактировать роадмап и т.д.) — переключатель ролей в этой фазе не
  является границей безопасности, см. §2. Это следующий, отдельный и
  крупный план, если/когда концепция 5 представлений подтвердится
  использованием.
- **`Person` как логин-аккаунт** — не входит в рамки; если позже
  понадобится, чтобы человек из матрицы делегирования сам логинился и
  видел «свои» назначенные пункты роадмапа, это отдельное решение,
  завязанное на предыдущий пункт.
- **Полноценный таск-трекер** — `RoadmapItem`/`ProcessStep` с назначенным
  `Person` дают лёгкую видимость «кто чем занят», не замену Jira/Linear
  (нет подзадач, нет трудозатрат, нет спринтов).
- **Полноценная система инцидент-менеджмента** (эскалации, SLA, статус
  «сейчас идёт реагирование», уведомления) — `ActionPlan` (§3) сознательно
  остаётся статичным текстом-инструкцией, написанным заранее и спокойно, а
  не live-инструментом отслеживания текущего инцидента.
- **ML/кластеризация для поиска «возможностей интеграции»** между
  продуктами (§5) — только детерминированные правила (общий сегмент/
  категория JTBD) в первой итерации.
- **Мультитенантность/workspace-модель на компанию** — по-прежнему
  однопользовательская MVP-модель под капотом (`plans/backlog.md`); пять
  представлений в этом плане — разные *линзы* на одни и те же данные, не
  разные организации.
