# План визуального редизайна RPM Platform

Составлено 7 августа 2026 по запросу: сделать платформу визуально убедительной — «чтобы выглядело так, будто её сделали профессиональные фронтенд-разработчики» — без существенных изменений бэкенда. Это план **дизайн-системы и полировки компонентов**: Prisma-схема, Server Actions, роуты и бизнес-логика не трогаем; меняем `app/globals.css`, `tailwind.config.ts`, `components/ui/*` и точечно — разметку/классы в `components/forms`, `components/shared`, `components/jtbd-graph`, `components/hypotheses`.

**Обновление (уточнение объёма):** цель — не косметическая доводка токенов, а ощутимый визуальный скачок. Токены (§4) — это фундамент, на котором стоят более смелые, коммитящиеся решения: реальный редизайн карточки узла JTBD-графа (§4.4 — сейчас перегружена текстом), собственная система иконографии вместо голого цвета+текста, дашборд как осмысленная композиция, а не сетка одинаковых плиток, и явная витрина уже существующей (но никак не обозначенной) фичи — клавиатурных сокращений. План остаётся в рамках «без изменений бэкенда», но внутри этих рамок — не минимальный, а максимально доведённый до профессионального уровня набор решений.

## 1. Аудит текущего состояния

Проверено вживую (скриншоты дашборда, графа JTBD, kanban гипотез, формы создания продукта) поверх кода `app/globals.css`, `tailwind.config.ts`, `components/ui/{button,card,badge}.tsx`, `components.json`.

**Диагноз: это на 100% нетронутый shadcn/ui CLI-скаффолд** (`npx shadcn add button card badge` — byte-for-byte дефолтные варианты) с одним замененным токеном — `--primary` перекрашен в красный. Отсюда узнаваемый «сделано ИИ/шаблоном» эффект:

- **Нативные `<select>` без единой стилизации** — на скриншоте формы создания продукта и фильтра графа JTBD видны голые браузерные дропдауны с системным шрифтом и квадратной стрелкой — самый режущий глаз элемент во всём интерфейсе.
- **Карточки — плоский `border` + `shadow-sm` дефолт shadcn**, различие только в цвете `border-t-4` сверху. На дашборде это создаёт эффект «раскрашенных прямоугольников», а не продуманной иерархии карточек.
- **Типографика не реализует свой потенциал.** В проекте уже подключены три шрифта с прицелом на характер — Manrope (дисплей, 600–800), Inter (текст), IBM Plex Mono (`--font-mono`) — но `font-mono` нигде фактически не используется (числа на дашборде, номера исследований `#31`, даты, ID — всё живёт в Inter), а `font-display` применяется только к `h1–h3` без развитой шкалы (нет выраженной разницы в отслеживании/интерлиньяже между уровнями).
- **Тёмная тема полностью описана в CSS, но не подключена нигде** (задокументировано ещё в `plans/backlog.md`) — де-факто выброшенная работа.
- **Сигнальная система цветов (`--signal-violet/red/blue/slate`) — по факту хорошая, недооценённая идея** (см. `app/globals.css` и `lib/signal-colors.ts`), но применяется только к типам JTBD и паре бейджей — не стала сквозным языком статусов/приоритетов.
- Формы — голые `<input>`/`<textarea>` с дефолтным `border-input`, море пустого пространства без ритма (форма создания продукта — узкая колонка слева, справа пустота на весь экран).
- Kanban и граф JTBD (React Flow) — самое визуально плотное и «профессиональное» место интерфейса уже сегодня; их не нужно переизобретать, только подтянуть к новой системе токенов.

## 2. Что говорят тренды 2026 (сжато)

- **Decision-ready, не decorative.** Тренд enterprise/B2B UI 2026 — «progressive disclosure» и «показывать минимум для решения, раскрывать по запросу», а не наполнять экран декором. Источник: [B2B SaaS Design Trends 2026](https://procreator.design/blog/b2b-saas-design-trends-and-examples/), [Enterprise UX Design Guide 2026](https://fuselabcreative.com/enterprise-ux-design-guide-2026-best-practices/).
- **Плотные данные — это нормально, если управляемо.** Для таблиц/списков — реальные `<table>` с семантикой, выравнивание чисел по правому краю, `tabular-nums`, регулируемая плотность (compact/comfortable). Источник: [Data table UI design reference guide 2026](https://www.setproduct.com/blog/data-table-ui-design).
- **Тёмная тема — не опция, а ожидание для инструментов с долгими рабочими сессиями.** Источник: [SaaS UI Design Trends 2026](https://www.saasui.design/blog/7-saas-ui-design-trends-2026).
- **Как не выглядеть «сгенерированным ИИ»:** переопределить 4–5 ключевых токенов (радиус, primary, плотность, тени), а не оставлять дефолт; добавить один «фирменный» несистемный штрих (своя тень, своя кривая transition, нестандартная деталь), которого нет в дефолтном ките; убрать типовой набор `rounded-2xl shadow-lg p-6`, который встречается в любом ИИ-сайте. Источник: [why shadcn looks generic and how to fix it](https://freedesignmd.com/blog/shadcn-looks-generic), [how to fix the "AI-generated" look](https://dev.to/alanwest/how-to-fix-the-ai-generated-look-in-your-frontend-1ahh).
- **Headless-компоненты + Tailwind + CVA — по-прежнему стандартный стек** для стилизованных select/dropdown/combobox (Radix Primitives, на которых и построен shadcn) — то есть решение «под рукой», не требует новой библиотеки. Источник: [Radix UI headless components](https://webfield.io/radix-ui).
- **Числа/данные — моноширинным шрифтом там, где нужна сканируемость и выравнивание** (ID, счётчики, даты, проценты) — устоявшийся паттерн у дата-инструментов.

## 4. Дизайн-направление

### Цвет

Не меняем бренд-якорь (красный на белом, привязка к Rutoken — уже осмысленный, не шаблонный выбор), но **уточняем палитру**, чтобы она перестала читаться как «дефолтный shadcn + один перекрашенный токен»:

- **Primary** — чуть более глубокий, «окисленный» красный вместо чистого ярко-алого (`hsl(0 72% 50.6%)` → `hsl(4 68% 42%)`, ближе к кирпичному/охра-красному) — меньше «кнопка из конструктора», больше «корпоративный акцент».
- **Canvas** — фон не чистый `#FFFFFF` (`0 0% 100%`), а едва тёплый off-white (`hsl(30 20% 98.5%)`) — на глаз почти белый, но с ощущением спроектированности; карточки (`--card`) остаются чистым белым, создавая мягкую глубину без теней.
- **Border** — тоньше и холоднее текущего (сейчас `214 25% 90%`, довольно заметный) — почти волосяная линия (`220 14% 91%`), как в Attio/Linear.
- **Сигнальная палитра остаётся как есть** (`--signal-violet/red/blue/slate`) — она уже хороша, доводим её применение, а не сами цвета.
- **Тёмная тема** — не с нуля: существующие `.dark`-токены в `app/globals.css` берём за основу, но уточняем так же, как светлую (глубина фона, острота бордеров), и — главное — **наконец подключаем** (см. §6).

### Типографика

Не меняем шрифтовую тройку (Manrope/Inter/Plex Mono — уже нешаблонный выбор), но выстраиваем **настоящую шкалу и роли**:

- **Manrope (display)** — заголовки `h1–h3`, названия карточек-модулей на дашборде, заголовки колонок kanban. Сейчас используется вес 600–800 почти без разницы между уровнями — развести: `h1` 700/tight tracking, `h2` 700, `h3` 600, с чётко разным `font-size`/`line-height` (сейчас шкала фактически дефолт Tailwind).
- **Inter (текст)** — тело, лейблы форм, описания — без изменений, это верно выбранная рабочая лошадка.
- **IBM Plex Mono (данные)** — начинает реально использоваться: номера исследований (`#31`), даты, счётчики на карточках дашборда (сейчас `font-mono text-3xl` уже частично применяется к цифрам — расширить на ID/slug'и/даты/проценты аудитории сегмента/приоритет гипотезы), метки статуса в kanban. Это и есть узнаваемый приём «дата-инструмента» — моноширинные данные рядом с гуманистическим текстом.

### Слой/тень/радиус

- Радиус чуть меньше текущего (`0.5rem` → `0.375rem` для карточек/инпутов, `9999px` оставить только для бейджей/пилюль) — меньше «слащавости», ближе к рабочему инструменту.
- Вместо `shadow-sm` по умолчанию на всех карточках — **тени только на интерактивных/поднятых элементах** (hover-карточки модулей, открытые dropdown, модальные слои); статичные карточки списков — просто тонкая граница без тени. Это ровно то отличие, которое отделяет «сделано вручную» от «дефолт библиотеки».
- Один **фирменный, нигде не задокументированный в shadcn токен** (см. тренд «add a unique token» из §2): единая кривая transition `cubic-bezier(0.22, 1, 0.36, 1)` (в проекте уже используется в `card-settle` keyframe — расширить на все hover/focus-переходы кнопок, карточек, инлайн-полей) — «фирменная упругость» вместо дефолтного `ease`.

### Карточка узла JTBD-графа — разгрузить от текста

Сейчас (`components/jtbd-graph/jtbd-node.tsx`) один узел — это: заглавными буквами текстовая плашка типа задачи («БОЛЬШАЯ ЗАДАЧА»), галочка подтверждения эмодзи-символом, three-line-clamp заголовка мелким кеглем и ещё строка категории — всё в 224px-блоке, залитом сплошным цветом типа задачи. При 6+ узлах на графе (уже сегодняшний демо-объём) это читается как «стена текста в цветных прямоугольниках». План разгрузки:

1. **Тип задачи — иконкой, не словом.** Четыре типа JTBD получают по иконке из `lucide-react` (уже зависимость проекта): `Mountain`/`Layers` для «Большой задачи» (масштабная, не решается целиком), `Target` для «Основной» (то, что продукт закрывает полностью), `ArrowRightCircle`/`GitCommitHorizontal` для «Малой» (шаг на пути), `Dot`/`CircleSmall` для «Микро». Иконка + `title`-подсказка вместо строки заглавных букв — убирает целую текстовую строку из каждой карточки, тип всё равно считывается мгновенно (иконка + цвет вместе, а не текст).
2. **Цвет — акцентом, не заливкой.** Вместо сплошной цветной заливки всего блока (`backgroundColor: colors.bg` на весь узел) — белый/нейтральный фон карточки и цветной **левый бордер 3–4px** + цветная иконка. Меньше зрительного шума соревнуется с текстом заголовка, но тип задачи по-прежнему считывается периферийным зрением на графе.
3. **Заголовок — главный герой.** Увеличить карточку до 260–280px и дать заголовку 2 строки чуть крупнее текущего (сейчас `text-sm` в 3 строки) вместо 3 мелких — короче визуально, читается быстрее, при переполнении — многоточие (полный текст открывается кликом по узлу, как и сейчас).
4. **Категория — в подвал, как тег, а не текстом.** Хайрлайн-разделитель перед категорией, сама категория — маленькая моно-подпись (uppercase, `text-[10px]`, `font-mono`) вместо серой строки того же начертания, что и остальной текст — визуально другой «регистр», меньше конкурирует с заголовком.
5. **Подтверждено исследованием — маленький сигнальный индикатор** (закрашенная точка/иконка `CircleCheck` фиксированного размера в углу), а не эмодзи-галочка внутри строки текста.

Итог — три чётких зоны на карточке (иконка+тип слева сверху / заголовок по центру / категория-тег снизу) вместо одного сплошного текстового блока, без изменения логики графа (React Flow, drag, связи — не трогаем).

### Иконография — сквозная система, не разрозненные точки

Сейчас `lucide-react` уже в зависимостях, но используется в 4 местах (`site-nav`, `copy-link-button`, `pin-button`, `print-button`) — почти нигде, где иконка реально помогает считывать интерфейс. Профессиональный дата-инструмент везде спаривает иконку с текстом, а не полагается на цвет/текст в одиночку:

- По иконке на модуль дашборда (Продукты/Исследования/Сегменты/JTBD/Гипотезы/Разговоры/Инсайты/Конкуренты/Фичи/Маркетинг) — рядом с названием карточки, не вместо него.
- По иконке на статус гипотезы в kanban-колонках и на детальной странице (сейчас — только цветная точка).
- Иконки типа JTBD — см. выше.
- Единый набор — 16px, `stroke-width: 1.75`, цвет наследуется от текста/акцента — без микса «то обводка, то заливка».

### Клавиатурные сокращения — сделать видимой фичей, а не секретом

В проекте уже есть полноценная система горячих клавиш (`components/shared/keyboard-shortcuts.tsx`, `g` + буква для переходов, `n` для создания) — но нигде в интерфейсе не подсказывается, что она существует. Это ровно тот вид детали, который выдаёт «сделано профессионалами» (Linear, Superhuman, Notion — все выставляют клавиатурный слой напоказ): маленькая подсказка `G` рядом с полем поиска в `SiteNav`, открывающая по клику/по `?` компактный оверлей со списком сочетаний (данные уже есть в `docs/user-guide/recommendations.md`, просто нет UI-поверхности). Правки — только новый Client Component + немного разметки в `SiteNav`, `KeyboardShortcuts` не меняет поведение.

### Дашборд — композиция, а не сетка одинаковых плиток

Сейчас все 10 модулей — визуально одинаковые карточки разного цвета рамки, включая единственный продуктовый модуль (в масштабе 1 продукт на пользователя) наравне с остальными. Дать дашборду настоящую иерархию:

- Главный продуктовый блок — не карточка-плитка, а полноширинный «заголовочный» блок с именем активного продукта, стадией и коротким summary (использует уже существующие данные, без новых запросов).
- Группы «Исследование клиентов» / «Позиционирование» — плитки остаются, но с иконками (см. выше) и более плотной сеткой.
- «Закреплённое» / «Последняя активность» — из карточки-в-карточке в hairline-список (см. §5) с иконкой типа записи вместо текстового `Badge`.

### Фирменный элемент («подпись» интерфейса)

У проекта уже есть внутреннее название для сигнальной системы — «Реестр» (см. комментарий в `globals.css`, ссылающийся на `growth-plan.md §2.7 "Реестр"»). Это точный образ для инструмента структурированного учёта: пронумерованные записи (`#31` у исследований), связи между сущностями (граф JTBD — уже сильнейшая визуальная часть продукта), сигнальные пометки статуса. **Сигнатурный приём редизайна** — сделать это явным сквозным языком, а не спрятанной деталью:

- Моноширинные ID/номера везде, где они есть в данных (не только у исследований — добавить короткий отображаемый ID и в другие детальные страницы, чисто на уровне вёрстки, без изменения схемы).
- Хайрлайн-разделители вместо card-границ там, где уместно (списки, а не сетки карточек).
- Единый визуальный вокабуляр «сигнальных» точек/полосок статуса (уже используется точечно — цветная полоска слева у `SectionHeading`, цветной верх у карточек модулей, цветная рамка узла графа) — свести к одному повторяющемуся приёму вместо трёх разных.

```
                                        └─────────────────────────┘
```

(Иллюстративно — точная раскладка уточняется в реализации; ключевая идея — не всё должно быть карточкой-плиткой с цветной рамкой, список/реестр может быть плотнее и «взрослее».)

## 6. Фазы

### Фаза 1 — Фундамент токенов

Эффект виден сразу на 100% экранов, без правки разметки страниц.

1. `app/globals.css` — уточнённая палитра light/dark (§4: primary, background, border, тени), расширенная шкала типографики (`h1–h6` с разными `font-size`/`line-height`/`letter-spacing`, не дефолт Tailwind), единая transition-кривая как CSS-переменная.
2. `tailwind.config.ts` — уменьшенный `--radius`, кастомная `fontSize`-шкала, `letterSpacing`.
3. **Тёмная тема подключается по-настоящему**: переключатель в `SiteNav`, сохранение в `localStorage`, дефолт — системная `prefers-color-scheme`, инлайн-скрипт в `app/layout.tsx` до первой отрисовки (без FOUC). Закрывает известный пробел из `plans/backlog.md` бесплатно в рамках этой же задачи.

### Фаза 2 — Примитивы `components/ui/*` и иконография

4. **`select.tsx`** — нативный `<select>` → Radix `Select` (`@radix-ui/react-select`) — самый заметный визуальный долг проекта. API (`value`/`onChange`/`children`-опции) не меняется, вызывающий код в `components/forms/*` не трогаем.
5. `button.tsx` — чёткие варианты (`default`/`outline`/`ghost`) через тень+цвет, а не только `hover:opacity-90`; видимый `focus-visible:ring`.
6. `card.tsx` — два паттерна вместо одного: «плитка модуля» (hover-тень, для дашборда) и «карточка контента» (только hairline-граница, для форм/деталей).
7. `badge.tsx` — сигнальная палитра (`--signal-*`) как варианты бейджа напрямую, объединяя с `JobTypeBadge`/`SignalBadge`.
8. `input.tsx`/`textarea.tsx` — точный `focus` (кольцо + граница одновременно), контрастнее `placeholder`.
9. **Иконография как система** (см. §4) — набор `lucide-react`-иконок на модули дашборда, статусы гипотез, типы JTBD; единый размер/толщина обводки.

### Фаза 3 — «Герои»: самые заметные, самые смелые решения

Здесь — то, что реально меняет впечатление «сделано на коленке» → «сделано профессионалами», не только полировка.

10. **Карточка узла JTBD-графа** (см. §4) — три чётких зоны вместо стены текста: иконка типа вместо текстовой плашки, цветной акцент-бордер вместо сплошной заливки, 2-строчный увеличенный заголовок, категория — моно-тег в подвале за хайрлайном.
11. **Дашборд как композиция** (см. §4) — продуктовый блок перестаёт быть такой же плиткой, как остальные 9 модулей; «Закреплённое»/«Последняя активность» — hairline-список с иконками вместо карточки-в-карточке.
12. **Kanban-карточки** (`components/hypotheses/kanban-board.tsx`) — статус-иконка + моно-дата + текст вместо только цветной полоски; hover/drag-состояние с тенью (расширить существующую `card-settle`-анимацию на drag-start).
13. **Клавиатурные сокращения — видимая фича** (см. §4) — подсказка `G` у поля поиска, оверлей со списком сочетаний по клику/`?`.
14. Граф JTBD (панели/легенда, не логика React Flow) — привести к уточнённой палитре Фазы 1.

### Фаза 4 — Остальные экраны (проход по хвосту)

15. Формы (`components/forms/*`) — реальная сетка (2 колонки на широких экранах вместо узкой колонки с пустотой справа), визуальная группировка связанных полей.
16. `SiteNav` — более выразительное состояние активного таба (не только подчёркивание).
17. Списки (`/research`, `/segments`, `/competitors` и т.д.) — где уместно, сетки карточек → плотные таблично-подобные списки с hairline-разделителями (тренд «плотность», §2), начиная с самых длинных списков.
18. Точечный проход по оставшимся детальным страницам — приведение к общей системе (Фазы 1–2 уже дают им большую часть эффекта автоматически через переиспользуемые примитивы).

## 7. Что осознанно вне рамок

- Никаких изменений `prisma/schema.prisma`, `lib/actions/*.ts`, роутов — чисто слой представления.
- Не меняем 5 моделей навигации/архитектуру страниц — только визуальную огранку существующих экранов.
- React Flow (граф JTBD) — не меняем логику/поведение, только палитру узлов/легенды.
- Новая зависимость только одна — `@radix-ui/react-select` (та же семья Radix Primitives, на которой уже стоит shadcn/ui, архитектурно ничего нового не появляется). `lucide-react` для иконографии уже в проекте.

## 8. Порядок внедрения и проверка

1. Фаза 1 (токены) — один проход, эффект виден сразу на всех страницах без правки разметки.
2. Фаза 2 (примитивы + иконография) — после токенов, поскольку примитивы их потребляют; тёмная тема требует ручной проверки каждого примитива в обеих темах (визуальный QA, не автотест).
3. Фаза 3 («герои») — самая заметная при демо часть: JTBD-узел, дашборд, kanban, клавиатурные подсказки.
4. Фаза 4 — постранично добираем оставшееся (формы, списки, детальные страницы) — во многом достаётся «бесплатно» от Фаз 1–2 благодаря переиспользуемым примитивам.
5. Проверка на каждом шаге: `npm run lint && npm run typecheck && npm run test:e2e` (уже существующий Playwright-набор ловит регрессии в разметке — например, если Radix Select сломает `getByLabel`/`selectOption`, это увидит CI немедленно) плюс визуальный проход по обеим темам вручную/скриншотами.
6. Обновить `docs/user-guide/recommendations.md` (убрать пункт «тёмная тема нигде не включается») и `PROJECT_STATE.md` после Фазы 1; добавить строку о клавиатурных сокращениях как видимой фиче после Фазы 3.
